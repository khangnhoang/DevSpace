# Push, PR, CI and merge

Read this before any push, PR creation or update, check watching, CI failure or merge. Grants are owned by `AGENTS.md` section 4; the narrowest mode the Owner stated applies (`docs/agent-loops.md` Loop 3).

Select tools under [AGENTS.md, Tool selection](../../../../AGENTS.md#tool-selection), and apply its [section 4 delivery boundary](../../../../AGENTS.md#4-permissions) throughout this procedure.

## Preconditions

Before any PR or CI action run `git status -sb`, `git branch --show-current`, `git remote -v`, `gh --version` and `gh auth status`, and confirm the remote and the authenticated account are the ones the task means (`khangnhoang/DevSpace`). Stop and report when:

- the worktree is dirty and the task did not include those changes, or the branch is unclear or wrong for the task;
- no usable Git remote exists, `gh` is missing, or `gh auth status` fails or shows no usable account;
- `gh` output shows missing scopes or token permissions, or the Windows keyring is not reachable from the current shell;
- proceeding would print or expose a secret.

Do not install or authenticate `gh`, switch to the raw REST API, or copy a token as a workaround; report the blocker and the smallest thing the Owner must do. These stops grant nothing: the action itself still needs its own grant.

## Push

Needs a push grant (`AGENTS.md` section 4). Before a normal push confirm: clean worktree and index; the exact branch and commit range; the configured upstream; refreshed remote state with ahead/behind counts; and that a normal push is enough (force-push is never implied). After it, check that the remote head equals the local head and divergence is `0 behind / 0 ahead`. For multi-checkpoint work, push once after the final self-review passes and later push only correction commits, each after its own self-review.

## Create or update a PR

1. Build the content from evidence: `git log --oneline main..HEAD`, `git diff --stat main...HEAD`, the plan, progress and the checks that really ran. Do not invent tests, QA, decisions or risks; mark unknown what you cannot confirm.
2. Check that the head branch is already on the remote. If not, stop and ask for push permission. Never accept an interactive `gh` offer to push or fork.
3. Check for an existing PR (`gh pr view <branch>`); never create a duplicate. Update title, body, labels or draft state only as asked.
4. Create with `gh pr create --base main --head <branch> --title "<title>" --body-file <file>`; update with `gh pr edit`. Use an exact title or body when the Owner gives one. Otherwise title and body follow the language rule in `AGENTS.md` section 1. Keep the body file out of the commit.
5. The body follows `.github/pull_request_template.md`: Summary, Changes, Checks run, CI result, Production impact and pending hosted steps, Risks and limits, Follow-ups. `gh pr create --body-file` does not apply the template, so build the body file from it; leave `CI result` as the placeholder table until CI ends (see "Record the CI result"). Link the plan or problem IDs.
6. After a PR exists, inspect status and handle any authorized CI fix using the shared Tool selection rule linked above; do not poll with scheduled tasks. When the Owner says to wait for CI, watch in the foreground (Watch CI).

Creating, updating, pushing and merging are separate grants (`AGENTS.md` section 4).

## Watch CI

CI runs on every PR to `main`, with no hosted secret; a push to `main` (a merge) starts no `ci.yml` run, so read a PR's result for the head that was merged; a merge starts only the `production-gate` workflow ([Production gate](#production-gate)). `.github/workflows/ci.yml` has the jobs `typecheck`, `build`, `docs`, `lint`, `db` and `e2e`, listed by `gh pr checks` next to the Vercel deploy preview, which still runs as before. `typecheck` also runs `npm run typecheck:api`, `build` also runs `npm run build:api` and checks that neither the Next route manifest nor `dist` holds a test fixture, `lint` also runs `npm run lint:api`, `db` runs `npm test` (the `api` project among the rest) and then `npm run api:schema:check`, and `e2e` installs Chromium and runs `npm run test:e2e` (the app on 3100 and the fixture API on 3101); each command starts its own generated `devspace-test` stack on the runner (no separate `supabase start` or `db reset` step) and keeps its lock and run state in `/var/tmp`. All six jobs block. A seventh job, `changes`, is a helper and not a required check (see "Docs-only pull requests"). A red `lint` job means `npm run lint` or `npm run lint:api` reported a problem (errors and warnings alike, `--max-warnings 0`), listed in the step's log, or setup (checkout, Node, `npm ci`) failed. A red `db` job is a real failure: read the failing step in `gh run view <id> --log-failed`. A failed `npm test` step means the test stack did not come up or reset (the log names the missing container, or the SQL error of the baseline, a migration or the seed), a test failed, a known bug stopped reproducing (the message names the known bug's ID), an `api` row failed (the run starts the API, so a missing build or a refused environment shows first), the rls setup failed (stack, host check or sign-in), or the run ended unclean (the log prints the cause, such as residue found by the end-of-run audit). A failed `npm run api:schema:check` step, after a passing `npm test` step, is not a test failure. Read its log: only the line saying the files differ from the test stack's schema means the committed `backend/src/db/schema.ts` or `relations.ts` lags the migrations (regenerate with `npm run api:schema:pull` on the dev stack after the migration, and commit both files). A `drizzle-kit pull failed` line or a test-stack start or lock error is a tooling or stack failure, classified by its own step and error (CI failure below). A red `e2e` job is a real failure too: a failed `npx playwright install` step is the environment, and a failed `npm run test:e2e` step is a stack start or reset failure (same reading as `npm test`), a failing row, a hosted or page-error hit of the network guard, or a build or server failure (the Playwright output is in the step's log; when Playwright ran and the job failed, the HTML report is the workflow artifact `playwright-report`, and a failure before Playwright ran uploads nothing). A passing `npm test` prints a `known bug <id>` line for each open known bug; CI uses Vitest's default reporter, so they show in the step's log. Whether `main` requires the blocking jobs is an Owner setting in GitHub, not something the repo enforces; check it with `gh api repos/khangnhoang/DevSpace/branches/main/protection` (read-only).

When the Owner says to wait for CI, run `gh pr checks <n> --watch --interval 30` in the foreground, rerun it if the shell timeout ends it first, and keep the turn open until every check is terminal ([Loop 3](../../../../docs/agent-loops.md#loop-3-pr-and-ci)). Otherwise use `gh pr checks --watch` (or `gh pr checks`). Report each check's exact terminal state. Do not say CI passed unless GitHub shows a passing state; report pending, failed, skipped and cancelled explicitly with the job names and a short log summary. A failed job's log comes from `gh run view <id> --log-failed`.

## Docs-only pull requests

On a pull request to `main` the `changes` job runs `scripts/ci/docs-only.mjs`, taken from the base commit (a change to the script takes effect on the PRs after it merges; a base without it fails the job, so both jobs run), on the changed paths (`git diff --name-only -z --no-renames`, base to head). When every path ends in `.md` or is exactly `.claude/skills/playwright-cli/LICENSE`, `db` and `e2e` are skipped and `typecheck`, `build`, `docs` and `lint` still run. The list lives only in that script (`DOCS_ONLY_FILES` and the `.md` rule), tested in `__tests__/unit/docs-only.test.ts`; any other file, also a script or image under `docs/` or `.claude/skills/`, runs all six jobs, and so does an empty list.

Fail-open: `db` and `e2e` are skipped only when the `changes` job succeeded with output `true`. A failed or skipped `changes` job and a missing output run both; a cancelled run starts neither. GitHub counts a job skipped by its own `if:` as passed for the required checks, so a docs-only PR stays mergeable. Read a skipped `db` or `e2e` as "docs only, not run", never as a test result. A skipped row is expected only on a docs-only PR; on a PR that changes code it means the classifier or the condition is wrong, so report it as a blocker.

## Record the CI result

Under a grant to create or update that PR, when its CI reaches a terminal state, red or green, Main writes the result into the body's `CI result` section with `gh pr edit <n> --body-file <file>`. An `inspect` or `watch` request alone writes nothing: Main reports the result in chat. After the write Main stops, unless the Owner separately granted a next action for this PR (a merge, a CI fix), which then proceeds only once its own gates pass. What this write may cover, and who may merge or fix a red result, is owned by `AGENTS.md` section 4.

- Report the latest run for the PR's current head, not an older or cancelled one: the run link, the event, the head commit, and the table Check | Result | Duration | Notes with the Actions jobs (the six required ones; `changes` is optional) and Vercel.
- The `lint` row says pass or fail; on a failure, Notes names the first problems from the step's log.
- A check that did not reach its step says `not run`, `skipped` or `cancelled` with the reason (for example lint not run when setup failed).
- On a docs-only PR the `db` and `e2e` rows say `skipped` with the reason "docs-only PR, `changes` output true"; do not write `passed`.
- CI evidence lives in the PR body, not in a program's `progress.md` State.

## CI failure

Read the failed logs first (`gh run view <id> --log-failed` for an Actions job, or the Vercel build log). Classify as one of: `branch-caused-small-safe`, `branch-caused-large-risky`, `unrelated-main`, `infra-flaky`, `secret-env-config`, `db-risk`, `unclear`. Only `branch-caused-small-safe` may be fixed, under the CI-fix limits in `docs/agent-loops.md` Loop 3 and `AGENTS.md` section 4. A fix attempt is one cycle: read logs, edit, validate locally, commit, push, re-watch. It never widens the PR, touches schema, RLS, migrations, secrets or repo settings, weakens a check, forces a push or deletes a branch. Any other class: stop and report the job, the log evidence, the class, why it was not self-fixed and the smallest decision needed.

## Production gate

Read this after a merge, and when a `production-gate` run fails or never appears. The workflow `.github/workflows/production-gate.yml` runs on every push to `main` (one job, `production-gate`, no secret, not a required pull-request check), and Vercel keeps the production domain on the previous deployment until it passes. The pass rule, the watch-path file it reads and the deploy order are in [ADR 0008 D10](../../../../docs/adr/0008-backend-architecture-and-hosting.md); the rule itself is `scripts/ci/production-gate.mjs`.

- **After a merge:** find the run (`gh run list --workflow production-gate.yml --branch main --limit 3`) and watch it in the foreground until it is terminal (`gh run watch <id> --exit-status --interval 30`, read-only like Watch CI). The merge's watch ends there; report the run link and its exact terminal state. A pass is the gate's result, not proof that the production domain moved: say what was actually read (Vercel state is read only where a plan grants it).
- **Reading a failure** (`gh run view <id> --log-failed`): a timeout message prints `M` (the merge), `W` (the latest watch-path commit at or before it), the last commit the API reported, the last answer's status and its `server` header. A reported commit behind `W` means the Railway build failed or is slow; an HTTP 4xx or 5xx means the production path (the rewrite, Vercel's firewall) did not reach the API; a reported commit unknown to the repository, or a `W` that is too old or never reached, points at a watch-path file that differs from the Railway dashboard. "superseded by" means a later merge's check already passed, and "no commit ... touches a Railway watch path" fails at once.
- **A failed or timed-out check keeps production on the previous frontend, and every later merge fails too** until a fix-forward backend merge that Railway deploys reaches the reported commit (for example a revert of the broken backend change), or the Owner uses Vercel's Force Promote, an Owner-only bypass that Main records as a milestone in the owning program's `progress.md` with the deployment and the reason. This is not a pull-request CI failure: no CI self-fix round applies; stop and report the run, the log evidence and the smallest decision needed.
- **A merge whose check never reports** (no run started, for example during a GitHub Actions outage, or a skip marker) is held with no timeout. Recovery: re-run the workflow for that commit once Actions works, the next merge (its own deployment supersedes the held one), or Force Promote.
- **Re-run rule:** a failed or never-reported `production-gate` run of an older commit is re-run (`gh run rerun <id>`) only while no later merge's `production-gate` run is in progress or has passed, no merge to `main` happens until that re-run is terminal, and a run that passed is never re-run; otherwise the next merge recovers. A run that failed only because an earlier run was still queued at its deadline is recovered the same way. A re-run changes remote state, so do it only when the Owner asked (`AGENTS.md` section 4).
- **No skip markers:** no merge commit message to `main` (the PR title becomes its body under `gh pr merge --merge`) carries `[skip ci]`, `[ci skip]`, `[skip actions]`, `[actions skip]` or `skip-checks: true`, because no run would start and Vercel would hold that deployment with no timeout.

## Merge

Default: do not merge; report that the PR is ready for the Owner. Merge or auto-merge only when the Owner asks in the current task. Before merging verify with `gh pr view <branch> --json mergeStateStatus,reviewDecision,statusCheckRollup` and `gh pr checks`: every required check passes for the current head (a `db` or `e2e` skip counts only on a docs-only PR, as above; a missing, unexpectedly skipped or pending check blocks), the Vercel Preview passes or meets the exception below, branch protection allows the merge, no conflicts, no requested changes or open review comments, no branch rule blocking, and every hosted step the rollout order puts before the merge completed (applied and postflight done; order in `supabase-migration`). If anything is inconclusive, do not merge and say what could not be verified. Use `gh pr merge <n> --merge` unless another method is requested, with no skip marker in the PR title or the merge message ([Production gate](#production-gate)). After a merge, watch its `production-gate` run until it is terminal; the merge's watch ends there.

A failed Vercel Preview is classified from its build or deployment log before any merge. A failure the PR causes (code, build or deployment configuration) and a failure of unknown cause block the merge. Only a verified cause independent of the PR, such as provider billing or infrastructure, may get an exception, and only when every required check meets its gate, branch protection allows the merge and the Owner approves the exception for that PR. The PR body's `CI result` keeps the failed Preview row with its evidence. A general merge grant never waives a failed Preview (agent-workflow AW-U15 Owner decision 3). Applying a migration is a separate step with its own grant (`supabase-migration`).
