# ADR 0008: Backend architecture and hosting for the techstack migration

Date: 2026-11-08. Status: Accepted by the Owner on 2026-11-08; amended on 2026-11-09 with the TM-U3 production results (D5, D11, Consequences) and with the narrowed program of master plan r5 (see the amendment under Decision); amended on 2026-11-28 with the production gate of master plan decision 17 (D10, Consequences).

## Context

The [techstack-migration](../programs/techstack-migration/plan.md) program moves DevSpace to Next.js, NestJS, PostgreSQL through Drizzle, and Better Auth (master plan Owner decisions 1 to 4). Its TM-U2 unit decides, in this ADR, the architecture that TM-U3 to TM-U12 build on, from throwaway local spikes (appendix C) and vendor pages read on 2026-11-08 (appendix D). Owner decisions that bind it: the new hosting cost is at most 10 USD a month (14); the reference stack is Vercel, Railway, Neon Free and Cloudflare R2, which the ADR compares and may replace (15); spikes run locally only, so latency and cold starts are measured in TM-U3 (16).

Facts at the time of the decision:

- Main's read-only snapshot of hosted metadata, 2026-11-08: Supabase region `ap-southeast-2` (Sydney), PostgreSQL 17.6.1.052, organization plan Free, database 14 MB, 31 Storage objects (TM-U1 drill). The public JWKS endpoint returns no keys, so hosted still signs with the legacy shared secret (HS256). The local CLI stack signs with ES256 and publishes a JWKS, so local and hosted differ. Vercel: Hobby plan, Node 26.x, Fluid compute, default function region `iad1` (Washington, D.C.).
- Today's code: cookie sessions through `@supabase/ssr` refreshed in `proxy.ts` with `getUser()`; the browser calls Supabase directly; the role comes from `profiles`; payment rules are database functions called with the service role; the one realtime use is the sidebar (`app/components/SidebarContent.tsx:104-120`); Storage holds only `avatars`.
- Vercel's functions run in `iad1` and the database in Sydney, so every query of a server-rendered page already crosses the Pacific, and learners are in Vietnam. This ADR fixes that mismatch (D11).
- Vercel limits the Hobby plan to non-commercial use, and DevSpace has a payment flow. Owner decision 18 (below) settles this for now.

Owner decisions made after the approved plan (2026-11-08; the plan stays frozen, State records them too):

- **18.** The frontend stays on Vercel Hobby. This holds on the condition that DevSpace is a graduation project and collects no real money. The Owner accepts the Hobby terms risk: Vercel may disable or remove a Hobby project with or without notice ([terms](https://vercel.com/legal/terms), last updated 2026-10-19). Exit: before any real money is collected, the Owner decides again, either Pro (20 USD per seat, outside the 10 USD cap) or a move to another host.
- **19.** Files are served from a public R2 bucket on the custom domain `devspace-assets.vocaspace.com`, on the Owner's existing Cloudflare zone `vocaspace.com`. No domain is bought (domain cost 0). Public images are not proxied through NestJS. The DevSpace bucket is separate from any VocaSpace bucket, and only files that may be public are served from it. The Owner creates the bucket and the DNS record. No agent touches VocaSpace resources (`AGENTS.md` section 4 keeps the VocaSpace project off limits).
- **23.** (TM-U3 plan) D5 pass condition (b), a real Gemini call of the longest supported length reaching the client, moves from TM-U3 to TM-U8 and must pass on the production topology before the merge that moves Gemini to the API. TM-U3 proves the transport with a timed handler only. Railway gets no `GEMINI_API_KEY` before TM-U8.

### D1 NestJS host

- **Chosen:** Railway Hobby (5 USD a month, 5 USD of usage included), region Southeast Asia (Singapore), one always-on replica (the optional sleep setting stays off), Express adapter. The service builds from the repository with the `.node-version` major (26): Railpack reads `.node-version` ([Railpack](https://railpack.com/languages/node/), 2026-11-08), but it lists only LTS versions as supported and does not mention 26, so TM-U3 proves the build and falls back to a Dockerfile on Node 26 if it fails. The spike ran the API on Node 26.13.0 (S3). The Vercel frontend reaches it only through D5. The service is public (Vercel is outside Railway's private network), so every route authenticates itself.
- **Rejected:**
  - Railway Free: 1 USD credit a month, 0.5 GB, no custom domain ([Railway pricing](https://railway.com/pricing), 2026-11-08). The measured idle memory of 171 MB (S5 with Better Auth; 96 MB without) costs about 1.7 USD of RAM a month at the listed rate, so the credit cannot cover a month.
  - Vercel Functions for NestJS (re-checked after Owner decision 18, since Hobby stays and its non-commercial terms no longer decide this): Vercel documents zero-configuration NestJS as one Function ([NestJS on Vercel](https://vercel.com/docs/frameworks/backend/nestjs), page dated 2026-08-10). The reasons that still hold, each from a Vercel page: (1) a Function has a 4.5 MB body limit and a 250 MB bundle limit ([limits](https://vercel.com/docs/functions/limitations), 2026-08-24), which fits avatar uploads and the Gemini call only with margin that TM-U3 would have to prove; (2) the Hobby usage caps (for example 1 million Function invocations, 100 GB Fast Data Transfer and 4 Active CPU-hours a month; past one, the feature is blocked for 30 days, [Hobby](https://vercel.com/docs/plans/hobby), 2026-09-14) would then cover the frontend and the API together, so one overrun stops both and G7 has no fallback inside the plan; (3) the Hobby terms risk accepted in decision 18 (disable "with or without notice") would take down the API in the same event as the frontend, where a separate Railway service survives it; (4) the docs give no cold-start figure, and the API is meant to hold a database pool. This is a closer call than the earlier "plan terms" reason suggested: reasons (1) and (4) are unmeasured, and (2) and (3) are about independence, not capability. Vercel Functions stay the alternative if Railway's cost or build fails (Reopens when).
  - Fly.io: 512 MB shared CPU is 3.69 USD a month with no platform fee, Singapore exists ([Fly pricing](https://docs.fly.io/about/pricing), read 2026-11-08, no page date). This is about 1.3 USD cheaper than Railway Hobby. Rejected only on operating effort (Dockerfile and `flyctl` workflow, no GitHub dashboard integration read); it is the first alternative if cost matters more.
  - Render: Singapore is a region ([regions](https://render.com/docs/regions), no page date). The Free web service spins down after 15 minutes with a roughly one-minute cold start and Free Postgres expires after 30 days ([Render free](https://render.com/docs/free), 2026-11-08). Paid, from the vendor's pricing file ([Render pricing](https://render.com/pricing.md), no page date): a web service under 1 CPU is 7 USD a month with 512 MB, a Postgres under 1 CPU is 6 USD a month with 256 MB (19 USD with 1 GB), the Hobby workspace is 0 USD, 5 GB of bandwidth is included and the overage is 0.15 USD per GB. The page does not say whether paid services stay always on. Rejected on cost: API plus database is 13 USD a month from TM-U11, over the cap, against about 6.3 USD of Railway usage at the same stage (appendix A); through TM-U10 Render is 7 against 5.
  - Koyeb (assessed on its pages dated 2026-05-27): Singapore is a region, and the Eco family is offered in Washington D.C., Frankfurt and Singapore ([instances](https://www.koyeb.com/docs/reference/instances)). The price in Singapore is read: `eco-micro` (0.25 vCPU, 512 MB, enough for the measured 171 MB) is 2.68 USD a month, `eco-small` (0.5 vCPU, 1 GB) 5.36; the Starter plan is pay-as-you-go with no platform fee stated, and the free instance exists only in Frankfurt or Washington ([pricing FAQ](https://www.koyeb.com/docs/faqs/pricing)). So Koyeb is **cheaper** than Railway through TM-U10 (2.68 against 5.00) and is a priced, viable alternative. Rejected for two evidenced reasons: (1) it has **no spending limit or usage alert** (the FAQ says a spending-limits feature is "in development"), so the 10 USD cap (Owner decision 14) cannot be enforced on it, where Railway offers a hard limit and an email alert; (2) the pages read do not say whether an Eco instance stays always on (the scale-to-zero page covers Standard and GPU only), what CPU model Eco has, or that Starter may run Eco in Singapore, and the API must be always on (G7). Its Postgres plays no part in this decision. **Reopens when:** Koyeb documents a spending limit or alert and states that Eco instances are always on; Koyeb is then the first alternative on price.
  - A VPS with Coolify: Hetzner CPX02 (1 vCPU, 1 GB) is 7.99 EUR a month excluding VAT in Singapore ([Hetzner](https://www.hetzner.com/cloud/regular-performance), 2026-11-08). Rejected: the Owner would run the OS, patches and backups alone for a price near the cap.
- **Vercel Hobby (Owner decision 18):** Vercel restricts Hobby teams to non-commercial personal use and counts "any method of requesting or processing payment from visitors of the site" as commercial ([fair use](https://vercel.com/docs/limits/fair-use-guidelines), 2026-09-14). The frontend stays on Hobby because DevSpace is a graduation project that collects no real money; the Owner accepts that Vercel may disable a Hobby project without notice, and that the payment flow in the app is exercised with no real money. **Exit:** before real money is collected, the Owner decides again: Pro (20 USD per seat, [Hobby page](https://vercel.com/docs/plans/hobby), 2026-09-14, outside the 10 USD cap) or a move of the frontend. - **Evidence:** S3, S5 idle memory; the pages cited above.
- **Reopens when:** the TM-U4 gate of D11 fails; Railway does not build or run Node 26; the monthly usage exceeds the included 5 USD by more than 3 USD; Railway changes the Hobby terms; or real money is about to be collected (decision 18).

### D2 PostgreSQL host

- **Chosen:**
  - TM-U3 to TM-U10: the existing Supabase Postgres (Free, Sydney, 14 MB) stays the only database, because the data, `auth.users`, the unmoved operations and RLS live there and nothing may move twice. NestJS connects through Supavisor's shared pooler in session mode (port 5432, IPv4 on every plan, prepared statements work; [connecting](https://supabase.com/docs/guides/database/connecting-to-postgres), 2026-11-08), with a pool of at most 5 connections for one replica. Nano compute lists 200 pooler clients and 60 direct connections ([compute](https://supabase.com/docs/guides/platform/compute-and-disk), no page date). The Free project may be paused after low activity in a 7-day period, is restored from the dashboard, and has no downloadable backups ([going into production](https://supabase.com/docs/guides/platform/going-into-prod), no page date; [pricing](https://supabase.com/pricing), 2026-11-08), so the existing manual backup before each hosted write stays the rule. **One-week pause (G7):** `/api/health` touches no database, so it cannot keep Supabase awake and is not used for that. The API has a second path, `/api/health/db`, that runs `select 1` through the pooler (it fails when the database is paused or unreachable). The alert is not a Supabase alert: it is an external keyword monitor on that path that emails the Owner, recommended as UptimeRobot Free (50 monitors, 5-minute interval, email alerts, 0 USD, [pricing](https://uptimerobot.com/pricing/), page dated 2026-10-28; swappable by the Owner, appendix A). Recovery: restore the project from the Supabase dashboard, then confirm `/api/health/db` and the app. Railway's own health check stays on `/api/health`, so a paused database does not put the API in a restart loop. **Not proven:** whether a daily `select 1` counts as activity for the pause (the page does not say whether API requests count); learner traffic is the only evidenced activity. If a pause happens despite the check, the fallback is the Pro plan (the page says it guarantees no pause; outside the cap) or moving the data to Railway PostgreSQL earlier than TM-U11.
  - From TM-U11: Railway PostgreSQL in the same Singapore region as the API, on a volume (volume price about 0.15 USD per GB-month; Railway lists volume backups every 24 hours kept 6 days, but does not say whether Hobby has them, [backups](https://docs.railway.com/volumes/backups), no page date). The data moves once, in TM-U11's downtime window. The TM-U11 plan re-reads the vendor numbers and runs a restore drill on the target before the move.
  - Fallback: Neon in `aws-ap-southeast-1` (Singapore; [regions](https://neon.com/docs/introduction/regions), 2026-10-14) as Free or Launch; or keeping the Supabase Postgres with its Data API disabled (master plan Outcome 3), in which case TM-U11 moves no data.
- **Rejected:**
  - Neon Free as the primary: 1 GB, 100 CU-hours, suspends after 5 minutes idle and cannot disable it, compute pauses until the next period at the limit ([Neon pricing](https://neon.com/pricing), 2026-11-08). A pause stops a payment app (G7), and no usage alert for the Free plan is documented in the pages read ([monitor usage](https://neon.com/docs/introduction/monitor-usage), 2026-10-09). A wake-up after idle adds a few hundred milliseconds ([latency](https://neon.com/docs/connect/connection-latency), 2026-11-04).
  - Neon Launch as the primary: no minimum, 0.106 USD per CU-hour and 0.35 USD per GB-month, and its alerts do not cap spending ([Neon pricing](https://neon.com/pricing), 2026-11-08). The cost is traffic-dependent, not fixed: an always-on 0.25 CU compute is about 182 CU-hours, about 19 USD a month, but with a pool idle timeout under 5 minutes compute sleeps between requests, and the bill is the active hours (illustration, traffic unmeasured: 150 active hours at 0.25 CU is about 4 USD plus 0.35 for 1 GB). So this is not rejected on price alone. Railway PostgreSQL wins on a predictable bill inside the Hobby plan (about 3.75 USD of usage, appendix A), no wake-up latency, and a private network with the API in one region. What Neon would give and Railway may not is a managed restore: Railway's page lists volume backups (daily, kept 6 days) but does not say Hobby has them ([backups](https://docs.railway.com/volumes/backups), no page date), while Neon's restore window on Launch was not read (Free: 6 hours). Mitigation on Railway: the Owner-run `pg_dump` before each hosted write and the TM-U11 restore drill. Neon Launch is the named alternative if Hobby has no volume backups and the Owner wants managed restore.
  - Supabase Postgres kept permanently: legal under Outcome 3, but it keeps a Sydney database next to a Singapore API for good, the Free plan pauses when idle, and the Supabase project stays a dependency. It remains the fallback.
- **Pooling and use:** one replica holding at most 5 connections is far under both the Supabase and Railway limits. Expected Neon CU-hours (the fallback pattern, an always-on API with a pool): a pool that keeps one connection open never lets compute suspend, so Neon Free burns 0.25 CU × about 730 hours, about 182 CU-hours a month, against 100 included, and compute stops about 17 days into the month (400 hours). With a pool idle timeout shorter than Neon's 5-minute suspend, compute sleeps between requests and the figure depends on traffic, which is unmeasured. This is why Neon Free is not the primary and why the fallback must use short idle timeouts.
- **Backup and the TM-U1 restore check, in two separate changes.** Today the runbook (`supabase-migration/references/backup-and-restore.md`) uses `supabase db dump --linked` (roles, schema, data of all schemas, history) and `supabase storage cp`, restored by `backup:check` into a Supabase scratch stack pinned to `hosted.json`, which compares the Supabase Storage objects too.
  - **TM-U10 (files) owns the file part.** When uploads switch to R2, new files land only in R2, so the unchanged runbook would miss them. TM-U10 therefore adds the R2 backup and its check in the same unit, before uploads switch: an S3-API copy of the bucket to the Owner's machine (tool chosen in TM-U10's plan), compared by object count, size and MD5 as the Storage check does today, covered by `backup:check` or a sibling command. Until a bucket is retired both are backed up. TM-U10 may run before TM-U9, so this does not wait for the database move. Pre-switch, the Supabase `avatars` copy and its check are unchanged.
  - **TM-U11 (database) changes only the PostgreSQL part.** The dump becomes `pg_dump` over the database's TCP proxy (which the Owner enables) from the Owner's PowerShell, and `backup:check` restores into a plain PostgreSQL container with no `auth`, `storage` or `supabase_migrations` schemas, comparing `public` counts and the Drizzle migration table. Until then the existing database runbook applies unchanged because the database is still Supabase.
- **Evidence:** the pages cited; the S4 role and schema results; Main's snapshot. No spike touched hosted.
- **Reopens when:** the TM-U11 restore drill fails, Railway Postgres usage pushes the monthly total over 10 USD, Hobby has no volume backups and the Owner wants managed restore (then Neon Launch), a daily `select 1` does not stop the Supabase pause, or Neon documents a Free usage alert and a cheaper wake-up.

### D5 Browser-to-API origin and cookies

- **Chosen:** the browser sees one origin, the Vercel origin (`devspace-lms.vercel.app` until the Owner adds a domain). `proxy.ts` calls `getUser()` as today and then rewrites `/api/*` itself with `NextResponse.rewrite`, copying the refreshed cookies onto that response. Dev: web `http://127.0.0.1:3000`, API `http://127.0.0.1:4000`. Test stack and e2e: web `http://127.0.0.1:3100`, API `http://127.0.0.1:3101` (TM-U3 may change the numbers). Production: API at its Railway public URL, named by `API_INTERNAL_URL`, never used by the browser. A Server Component calls `API_INTERNAL_URL` directly and forwards `cookies().toString()` after the proxy refreshed them; a server action that stays does the same and holds no business logic. Cookie: `sb-<ref>-auth-token`, `SameSite=Lax`, path `/`, not `HttpOnly` (the Supabase client reads it; observed in S1); the Better Auth cookie is `HttpOnly` and `Lax` (S5).
- **Cross-site POST defense:** `SameSite=Lax` already stops a different-site form from carrying the cookie; the API adds a guard for every non-GET request that carries a cookie: refuse if `Sec-Fetch-Site` is present and is not `same-origin`; otherwise refuse unless `Origin` is on the allow list; refuse if both headers are absent. The guard matters because a sibling origin on the same site is not stopped by `Lax` (S1: `127.0.0.1:4100` against `127.0.0.1:3200` sent the cookie and the guard refused with 403). Better Auth checks the origin itself (S5: 403).
- **Server-side callers:** a POST that a Server Component or a server action makes from the Next server is not a browser request and carries neither `Sec-Fetch-Site` nor `Origin`, so the guard would refuse it. The one shared API helper that those callers use (the only code allowed to call `API_INTERNAL_URL`) sets `Origin` to the app origin and forwards the cookie. This passes the guard through the same `Origin` allow-list rule, with no second rule and no new secret. Setting `Origin` in the helper is safe only if the request that entered Next was already checked, so the helper's use is limited:
  - **Server Components only read.** They run on a GET page load, so they never call a non-GET API path through the helper (a page load must not be able to cause a mutation).
  - **A mutation calls the helper only from a server action**, after Next's own Server Actions origin check. In the installed Next 16.4.3 (`next/dist/server/app-render/action-handler.js`, around lines 434 to 460; local code, **not Vercel evidence**) that check compares the request's `Origin` host with `x-forwarded-host` or `host` and aborts with `Invalid Server Actions request.` on a mismatch, unless the origin is in `serverActions.allowedOrigins`; when `Origin` is absent it lets the request through with a warning, because it treats it as a handcrafted request that cannot carry credentials that were not shared willingly. So a cross-site browser POST to a server action is refused by Next before our code runs, and it carries no `Lax` cookie anyway. A request with no `Origin` is not stopped by this check.
  - **A route handler**, if one is ever added, runs the same CSRF check as the API guard before it calls the helper.

  The claim stops there: the helper adds no protection of its own, and it is as safe as the callers above. **Not proven:** S1's server-side call was a GET. TM-U3 adds tests through Next, not only straight to the API: a cross-origin POST to a server action is refused and causes no API mutation; every page render by GET (all routes, signed in) makes no non-GET API call, checked from the API's request record; a server-side POST through the helper passes; the same POST without the helper's `Origin` is refused by the guard; a browser POST from another origin straight to the API is refused.
- **Bearer exemption:** the guard is skipped only for a request that is authenticated entirely by an `Authorization: Bearer` token and carries no `Cookie` header. A request that carries a cookie is always guarded, whether or not `Authorization` is present. No bearer client is planned in this migration; the rule exists so that none can be added by accident. TM-U3 tests a cross-origin POST with both a cookie and an `Authorization` header and expects 403.
- **Transport through the rewrite (what is proven and what is not):** S1 proved only small JSON. The facts below come from the installed Next 16.4.3 code in `node_modules` (local code, **not Vercel evidence**; Vercel executes its own routing for a deployed project): `experimental.proxyClientMaxBodySize` defaults to 10 MiB (`next/dist/server/config-shared.js`, `body-streams.js` `DEFAULT_BODY_CLONE_SIZE_LIMIT`), and when a body is larger, Next logs a warning and passes on **only the first 10 MiB** (the clone is ended, not rejected) in the self-hosted path used by `next dev`, `next start` and our e2e; the proxy to an external target times out after 30 seconds by default (`next/dist/server/lib/router-utils/proxy-request.js`, `proxyTimeout` 30000, overridable by `experimental.proxyTimeout`). The consequence is that an upload larger than the clone limit could reach NestJS silently truncated. Facts that size the problem (repository, read 2026-11-08): `next.config.ts` sets no `serverActions.bodySizeLimit`, no route segment sets `maxDuration`, the browser uploads straight to Supabase Storage today at `lib/supabase.ts:295`, `:334` and `:484` (so no upload passes through Next now), and the Gemini call is `ai.models.generateContent` inside a server action (`app/action/gemini.ts:49`) with no timeout set in the call.
  - **Gate.** TM-U3 sets the initial supported limits in its plan: the largest avatar or course image and the longest Gemini call. **Any unit that moves an upload or a long call behind the rewrite stays blocked until the contract below is proven on the production topology, and is re-proven when it changes a limit.** That is TM-U5 (avatar upload) and TM-U8 (course images, Gemini quiz generation), which move uploads and Gemini first, and TM-U10, and any later unit that does the same (techstack-migration decision 10 later kept both uploads direct, and decision 16 moved the profile out of TM-U5).
  - **Pass conditions (observing a behavior is not a pass).** (a) A valid payload up to the supported limit arrives byte-identical (hash compared at the API) for JSON of 1 MiB, 4 MiB and the supported maximum and for a multipart upload at the largest supported file. (b) The longest supported Gemini call completes and its answer reaches the client. (c) Over the limit, the request is refused explicitly (the API's own 413, and `Content-Length` compared with the bytes read so a truncated body is refused), never silently truncated. (d) A 35-second response and a streamed response are exercised and their behavior is recorded. A timeout, a truncation or a refusal on a case that is valid by (a) or (b) fails the test and keeps that path blocked from moving; it is not recorded as an acceptable finding.
  - Also tested there: 20 parallel requests with an expired cookie (concurrent refresh, below). Until the gate passes, uploads and Gemini actions stay on their current path.
  - **TM-U3 result (2026-11-09).** Condition (a) did not pass: through Vercel, JSON 4 MiB and a 2 MiB multipart upload answered 502 in one run of two, and JSON 1 MiB passed in both only after a stalled attempt; straight to Railway every row passed in one run. The mechanism inside Vercel is not known (techstack-migration TM-P17). The gate stands, so TM-U5, TM-U8 and TM-U10 re-prove the path before moving an upload. Conditions (c) and (d) and the 58-second transport passed. Binary bodies of 4 MiB through Vercel are unsupported. Concurrent refresh moved to TM-U5 (see Consequences), and then to TM-U13 (techstack-migration decision 19).
- **S1 result that changes the plan:** a `rewrites` entry in `next.config` does not return the proxy's refreshed `Set-Cookie`: the API received the new token, but the browser kept the expired cookie after an `/api` call (it updated only after a page navigation). Refresh-token rotation makes the next call spend the old refresh token again. That variant is rejected; doing the rewrite inside `proxy.ts` passed all 12 proofs in dev and in a production build (appendix C). The consequence for the real topology (Vercel's external rewrite, headers, timeouts) is unproven and is the first item of the AC6 proof.
- **Rejected:** a cross-site API origin (third-party cookies, CORS); a Next route handler that proxies `/api` (works but adds a function hop per call); the `next.config` rewrite (S1).
- **Evidence:** S1, S5.
- **Not proven (also in appendix C):** Vercel's rewrite to an external host for cookies, headers, body size, multipart and timeouts; concurrent refresh (two parallel `/api` calls with an expired cookie may both refresh with the same refresh token, and Supabase's rotation may reject the second or revoke the session; S1 refreshed with sequential calls only); a server-side POST through the helper.
- **Reopens when:** the production proof of AC6 fails on Vercel's rewrite (fallback: a catch-all route handler `app/api/[...path]/route.ts` doing the same forwarding; it keeps the one-origin and server-authorization invariants but adds a function hop and is not spiked), or Vercel documents refreshed cookies on `rewrites`.

### D6 Supabase session before TM-U9

- **Chosen:** method A. The session guard sends the access token to `GET /auth/v1/user` and trusts the answer, with a positive in-memory cache of 30 seconds keyed by a hash of the token, and a pre-check that refuses a token that is malformed or past its `exp` without a network call (refusal only; nothing is accepted from unverified claims). An operation of the payment or admin class skips the cache. Refresh stays with `proxy.ts` (D5); the API never refreshes. Supabase recommends this call for projects that sign with the shared secret and "strongly recommend[s] against" verifying locally with that secret ([JWTs](https://supabase.com/docs/guides/auth/jwts), 2026-11-08); hosted is such a project (snapshot).
- **What the spike showed (S2, dev stack):** A and C refuse expired, tampered, `alg: none`, malformed, empty, signed-out and deleted-user tokens; B accepts the signed-out and deleted-user tokens until they expire. Loopback cost per check, p50: A 3.96 ms, B 0.13 ms, C 1.18 ms. The cache is not spiked; it adds a staleness bounded by its 30 seconds for ordinary operations. The hosted round trip from Singapore to Sydney is not measured; it is the cost the cache amortizes and TM-U3 measures.
- **Two session checks per request:** `proxy.ts` still runs `getUser()` on every request it handles, `/api/*` included (D5), so an uncached API call makes two calls to Supabase Auth in Sydney: one from the Vercel function (`sin1`) and one from NestJS (Railway, Singapore). The NestJS cache removes only the second. Both are counted in the latency budget (D11), and TM-U3 measures them separately and together. If the pair breaks the budget, the unspiked options are to skip the proxy's check for an `/api` request whose access token is far from expiry (decode `exp` locally and refresh only near it) or to move to method C; neither is decided here.
- **Not proven:** that revoking a session (sign-out, deleted user) is refused by `/auth/v1/user` on the hosted project, which signs with HS256 (S2 ran the HS256 branch only with a locally signed token, and the dev stack signs ES256); refresh-token rotation under concurrent requests (D5); the rate limit of `/auth/v1/user` (not read).
- **Rejected:** B, local verification only (signed-out and deleted users stay valid up to the token lifetime, and it needs the shared secret in Railway); C, local verification plus a lookup of the session in `auth.sessions` through a `public` `SECURITY DEFINER` function (spiked and works, including HS256, but needs the legacy secret and a function that reads a managed schema, for code that TM-U9 deletes). `service_role` cannot read `auth.sessions` (S4), so C would need that function.
- **Reopens when:** the TM-U3 measurement shows `/auth/v1/user` too slow or rate limited (switch to C, whose code exists in the spike), or hosted moves to asymmetric signing keys (then local verification against the JWKS needs no shared secret; the ES256 path ran in S1 and S2).

### D7 Authorization model

- **Chosen:** the server checks are the enforcement: every endpoint authenticates the session, reads the role from `profiles` with its own query (never `user_metadata`), checks ownership in the query, and validates its body with the shared schema (master plan section 3, `server-actions` rules). NestJS connects as a new dedicated role `devspace_api`: `LOGIN`, not a superuser, `BYPASSRLS`, no DDL, with table and function privileges granted per moved operation (least privilege, widened by each unit's migration). RLS stays enabled on every table: it guards the unmoved Data API paths until each unit closes the old door and TM-U9 removes the last grants. The role does not exist yet; TM-U3 creates it in a Codex-gated migration under `supabase-migration`. The payment functions keep running in the database and are called by the API.
- **Re-proving an `rls` guarantee:** each row of `__tests__/rls` that covers a path a unit moves gets an API-level test (actor sessions minted for the test stack through the Admin API, the denied request posted to Nest, the table read back) before that path stops being the enforcement. The unit's plan carries the mapping from each `rls` row to its API test, and a row is deleted only after its replacement fails under a mutation of the check it covers.
- **Evidence (S4):** `service_role` (`NOLOGIN`, `BYPASSRLS`) reads `courses` and `profiles` through Drizzle by `SET LOCAL ROLE`; `authenticated` without JWT claims sees no `profiles`, which shows that a non-bypass role needs policies; `service_role` is refused on `auth.sessions`. These roles exist locally and match the shape of `devspace_api`; the dedicated role is named for TM-U3, not created.
- **Rejected:** connecting as `postgres` (owner, can change schema); connecting as `service_role` (cannot log in, and has the broad default grants of Supabase); running each request as `authenticated` with the user's claims so that RLS stays a live second layer (a transaction wrapper per request, policies written for `auth.uid()` that disappear with Supabase in TM-U9 and TM-U11, and two rule sets to keep equal).
- **Reopens when:** an API test cannot re-prove a guarantee. A missed server check found by review is fixed in the endpoint and gets an API test. RLS cannot be the second layer for `devspace_api`: `BYPASSRLS` makes every policy inert for it, so adding a policy to a table changes nothing for the API's own queries (it still guards the unmoved Data API paths). A live database second layer would need a different connection design, with `devspace_api` without `BYPASSRLS` and `SET LOCAL ROLE authenticated` plus the user's claims in each transaction, which is the rejected option above. That changes the server-side-authorization invariant, so it goes back to the Owner and is not a ready fallback.

### D8 Realtime replacement

- **Chosen:** remove Supabase Realtime. `user_progress` is written only by the learner's own browser (`checkAndSaveProgress` and the other writes in `lib/supabase.ts`; `app/action/admin-dashboard.ts` only reads it). After the progress write through the API returns, the page emits an in-page event and the sidebar refetches; it also refetches on `visibilitychange` and on window focus, and a `BroadcastChannel` tells other tabs of the same browser. Visible change: the sidebar still updates at once in the tab that completed the lesson; another device or browser updates when its tab regains focus, not instantly.
- **Rejected:** server-sent events from NestJS (Vercel documents `@Sse()`, [NestJS on Vercel](https://vercel.com/docs/frameworks/backend/nestjs), but it holds one connection per open tab for a low-value feature, and through the rewrite it is bound by Vercel's duration limit of 300 seconds on Hobby, [limits](https://vercel.com/docs/functions/limitations)); `LISTEN`/`NOTIFY` (needs a session-pinned connection through the pooler); keeping Supabase Realtime (breaks Outcome 3).
- **Evidence:** the code facts above; no spike was required.
- **Reopens when:** the Owner wants live cross-device updates (then SSE from the Railway service, outside the rewrite).

### D9 Drizzle

- **Chosen:** until TM-U11, `drizzle-kit pull` against the dev stack generates `backend/src/db/schema.ts` and `relations.ts`; the generated baseline SQL and `meta/` it also writes are deleted, never applied. Schema changes stay SQL files in `supabase/migrations` with rollbacks (master plan section 3); the schema is regenerated in the same PR, and a CI check regenerates it on the test stack and fails on a diff. Never `push`, `generate` or `migrate` against a Supabase database. From TM-U11, Drizzle migrations own the schema from a baseline pulled from the live database and compared with the catalog. Versions: `drizzle-orm` 0.45.4 and `drizzle-kit` 0.31.11 (Drizzle 1.0 is in release candidates per Better Auth's peer range; not adopted).
- **Verified by S4:** `pull` read-only produced 14 `pgTable` definitions in 373 lines (RLS policies as `pgPolicy`, foreign keys to `auth.users`) and created no `drizzle` schema; a read query through Drizzle ran as `service_role`.
- **Rejected:** Drizzle migrations before TM-U11 (two migration owners); hand-written tables (drift from the real schema).
- **Reopens when:** Drizzle 1.0 reaches general availability, or `pull` cannot represent a Supabase-only object the API needs.

### D10 API tests, CI and deploy

- **Test layers:** unit tests of pure logic; a new Vitest project `api` that runs Nest against the Supabase test stack (real database, real Auth), with actor sessions minted through the local Admin API (no typed password); Playwright e2e starts `next start` and the API together and exercises the rewrite. The API process gets a network guard like `server-guard.cjs`: it refuses any name resolution or connection outside loopback and records it, and external services (Gemini, mail) are replaced at their boundary. `npm test` and `npm run test:e2e` keep the lock, the reset rules and the audit.
- **CI:** the required checks keep their names (`typecheck`, `build`, `docs`, `db`, `e2e`, `lint`). The backend is added inside them (`tsc` of both packages, both builds, the `api` project in `db`, both servers in `e2e`); no job is renamed, and any new required job is the Owner's branch-protection change.
- **Deploy order (the mechanism).** Railway builds from the GitHub repository on a push to `main` when the push changes a file under a watch path, and Vercel builds the frontend from the same push, so one merge starts both with no ordering between them. **The production gate (master plan decision 17, TM-U16, amended 2026-11-28)** orders them. `.github/workflows/production-gate.yml` runs `scripts/ci/production-gate.mjs` on every push to `main`; the Owner's Vercel Deployment Check `production-gate` (blocks the production alias, production only) keeps the production domain on the previous deployment until the check passes. The check passes only when the commit that `/api/health` reports is the latest commit at or before the merge that touched a Railway watch path (a merge commit counts as itself, the commit Railway deploys), or a descendant of it, and a run waits for the runs of earlier merges, so checks pass in merge order; a timeout (20 minutes) or an error never passes. Therefore **one merge may carry a change's backend and frontend**: the previous frontend stays on the production domain while the new API deploys. The new API serves that previous frontend meanwhile, so an API change stays backward compatible: add first, remove in a later merge once no live frontend calls it. **Whatever the PR count, the migration order of master plan section 5 always applies:** an additive migration the new code needs is applied before that code merges; the restrictive migration that closes the old door is applied only after the frontend is live and the Owner's smoke check of the moved operations passed, and its old-endpoint refusal is then checked on production (`supabase-migration`, Rollout order). One case still splits the PRs, as **steps A to D**: a check that must run on the live API before the frontend switches (for example a check on a route the browser calls, such as TM-U13's refresh and cross-site checks under techstack-migration decision 19). Step A, a compatible backend merge (the new endpoints and additive migrations); step B, that check on production (the Railway deployment of the step A commit is healthy, `/api/health` reports its commit, the unit's smoke call answers as expected); step C, the frontend-switching merge; step D, the restrictive migration under the rule above. A unit that cannot be split this way is split in its plan or does not start. The gate's failure and recovery rules are in [pr-and-ci.md](../../.claude/skills/git-pr-workflow/references/pr-and-ci.md), Production gate.
- **Settings the Owner keeps in the hosting dashboards (names only).** Railway: service, region Singapore, GitHub connection, restart policy, health path `/api/health`, usage alert and hard limit (appendix A); variables `DATABASE_URL` (the session pooler), `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `ALLOWED_ORIGINS`, `GEMINI_API_KEY`; **"Wait for CI" off** (on, Railway would wait for `production-gate`, which waits for Railway, until the timeout); **watch paths** `/backend/**`, `/lib/schemas/**`, `/scripts/api/**`, `/package.json`, `/package-lock.json`, `/.node-version`, `/Dockerfile.api` and `/.dockerignore`. The gate reads them from `scripts/ci/railway-watch-paths.json`, a mirror of the dashboard, so a change to the watch paths is made in both places (a path Railway builds but the file lacks lets the gate pass before the API is live; a path in the file that Railway ignores makes later merges time out). Vercel: function region `sin1`, variable `API_INTERNAL_URL`, and the Deployment Check `production-gate` for production only (it must not hold a preview deployment, which the gate never runs for; see the unknown list below).
- **What Vercel does around the check.** Read (Vercel docs, 2026-11-27): a Hobby rollback goes only to the previous production deployment, at the routing layer without a rebuild, and stops automatic production domain assignment until `vercel promote`. Read (`vercel project checks --json`, 2026-11-28): the check is `production-gate` from GitHub Actions, blocks `deployment-alias`, targets production, `requires: none`, not re-requestable, `timeout` 5000 (the CLI help says seconds; what Vercel does when it expires is unknown). Observed (the first run of the workflow on `main`, 2026-11-27 19:04 UTC, merge `fb4ff73`): it passed on its first poll, and the runner's `git fetch` and the runs API with `actions: read` worked. Unknown, to be read or observed and recorded in the program's `progress.md`: whether a rollback or a redeploy of an older deployment runs the check again, what a re-run of a failed `production-gate` job does to the check Vercel holds, whether Vercel assigns the production domain to a deployment whose check passes after a newer production deployment went live (the gate's ordering stays either way, because it costs one API read), and whether a preview is held (to be observed on the first pull request after the check was added).
- **Rollback, after step C and before step D:** both doors are open, but the live frontend now calls the new endpoints, so rolling back only the API can remove endpoints it calls. The order is: roll the frontend back and confirm that the previous frontend is live, then roll the API back, unless the older API is shown compatible with the live frontend. The frontend rolls back by redeploying or rolling back its previous Vercel deployment (Instant Rollback is not assumed; a Hobby rollback is read above, and it stops automatic production domain assignment until a promote). A previous frontend still works because the old path is open. Before step C the API alone can be rolled back, by redeploying the previous Railway deployment, because the frontend does not call the new endpoints yet. **The gate after an API rollback:** the API then reports a commit that falls behind the latest watch-path commit, so every later merge's check fails until a fix-forward backend merge that Railway deploys reaches the reported commit, or the Owner uses Vercel's Force Promote (an Owner-only bypass that Main records as a milestone in `progress.md`). **The gate after a frontend rollback:** the gate is not involved in the rollback itself; what the check does afterwards is the unknown list above, and the next merge's own check decides its deployment.
- **Rollback, after step D:** the old frontend's Data API or Storage calls are refused, and an old API may lack the endpoints the new frontend calls, so rolling one side back alone breaks the app. The default is to fix forward. A full rollback undoes only the restriction first (the restriction's own `.down.sql`, which re-opens the old door), then rolls the frontend back, then the API. Additive schema from step A is undone only after every code version that depends on it is gone. The unit's plan names each command and who runs it. No rollback is claimed to work by default. Rolling the API back also makes the gate fail later merges, as in the paragraph above: fix forward, or Force Promote.
- **Rejected:** a separate CI workflow for the backend (new required-check names, a second Node setup); Vercel deploying the API (D1); a Railway deploy hook or API token for the gate (a secret and an Owner setting for no gain); Railway "Wait for CI" (the deadlock above); a gate that passes on timeout (it would let a frontend reach production without its API).
- **Reopens when:** the commit identifier cannot be exposed by `/api/health`, or Railway deploys a different commit than the merged one; Vercel stops offering the check from a `push` workflow or holds previews with it; or the first backend-touching merge under the gate (the proof in `progress.md`) shows the production domain moving before the check passes. The two-PR order of steps A to D then applies to every unit again, or the deploy order is decided again, for example by an Owner-instructed deploy after merge.

### D11 Cost and latency

- **Chosen:** monthly new cost 5.00 USD through TM-U10 and at most about 8 USD after TM-U11 (appendix A gives the formula, the margin and, for every service, what stops at its limit, the alert and the fallback). The frontend function region changes from `iad1` to `sin1` (Singapore): Hobby allows one function region ([regions](https://vercel.com/docs/functions/configuring-functions/region), 2026-08-11; `sin1` and `syd1` are listed, [region list](https://vercel.com/docs/regions), 2026-08-11). That is already closer to the Sydney database than Washington is, and next to the API. Region map in appendix B. NestJS goes to Singapore because it is the nearest Railway region to Vietnam (Railway lists four: California, Virginia, Amsterdam, Singapore; [regions](https://docs.railway.com/reference/regions), no page date) and the nearest Vercel and Neon region too.
- **Latency budget (set here, no vendor source; TM-U3 measures it and this ADR is amended if it fails):** p95 at the API for an authenticated read with at most 2 sequential queries ≤ 300 ms while the database is in Sydney (TM-U3 to TM-U10) and ≤ 150 ms after TM-U11; p95 end to end from Vietnam through the Vercel origin ≤ 600 ms and ≤ 400 ms. An uncached authenticated request pays two session checks (the `proxy.ts` `getUser()` and the NestJS check, D6), and the budget includes both. TM-U3 measures from the Owner's machine in Vietnam against production, 100 sequential and 20 concurrent requests each for `/api/health` (no database), `/api/health/db`, an authenticated `/api/session` with the NestJS cache cold and warm, the `proxy.ts` check alone, and a two-query read, recording p50 and p95. The Singapore to Sydney round trip, the Vercel external rewrite overhead and a cold Railway restart are unmeasured today.
- **If the budget fails during TM-U3 to TM-U10:** move the API to Fly.io `syd` or the Vercel functions to `syd1`, before moving the database earlier. The amendment below settles the TM-U3 failure without these moves; they stay options for the Owner if the TM-U4 gate fails.
- **TM-U3 result and amendment (2026-11-09).** The budget failed on production, measured from Vietnam: for the two-query read, sequential p95 633 ms at the API (limit 300) and 1842 ms end to end (limit 600), and 2167 and 3774 ms at 20 concurrent. Breakdown of p50, by subtraction and so approximate: the Vercel external rewrite about 540 ms (`/api/health` 815 ms end to end with the API doing no work, against `/login` 277 ms), the NestJS Auth call 165 ms (1 ms from the cache), the two queries about 440 ms (604 ms at the API, less the Auth call). The pool of 5 queues at 20 concurrent. What the `proxy.ts` check adds was not separated. The Owner decided: no region or database moves, because the moves above address the distance to Sydney and not the rewrite hop (an inference, not measured); 300 and 600 ms stay as targets and no longer gate TM-U3. **New gate:** TM-U4's first slice reads through the server helper, which does not cross the rewrite, and is measured on production; the p95 time until the page's data is visible may rise by at most 200 ms over the same page before the move (set here, no vendor source; master plan decision 12 fixes this measure, because the home page renders its data in the browser today and its HTML time is not comparable). A unit that makes the browser call `/api/*` for a screen re-measures first, since that path stays over budget until then. A failed TM-U4 gate returns to the Owner under this section.
- **Vercel and the cap:** appendix A shows the current Vercel and Supabase bills apart. Under Owner decision 18 Hobby stays and is not a new cost; Pro at 20 USD per seat, if the Owner chooses it before real money is collected, is outside the cap and a separate decision. Every `/api` call now also passes `proxy.ts`; whether that counts as an invocation against the Hobby cap of 1 million a month is not proven (appendix A).
- **Evidence:** appendix A and B; S5 for memory.
- **Reopens when:** a vendor price or limit in appendix A changes, or the TM-U4 gate above fails.

### D12 Better Auth placement

- **Chosen:** inside NestJS through the community package `@thallesp/nestjs-better-auth` on the Express adapter with `bodyParser: false`, the Drizzle adapter, `advanced.database.generateId: "uuid"`, `baseURL` equal to the D5 browser origin and `basePath` `/api/auth`, and custom `hash` and `verify` functions using `bcryptjs` so migrated Supabase hashes verify and new hashes stay compatible both ways. Starting versions proposed for TM-U9 (the lines S5 ran; the exact installed spike versions are in appendix C and are a different list; TM-U9 re-resolves and pins exact versions when it starts): `better-auth` 1.7.x, `@thallesp/nestjs-better-auth` 2.8.x, `@nestjs/*` 12.4.x, `express` ^5, `drizzle-orm` 0.45.x, `drizzle-kit` 0.31.x. The schema generator was `@better-auth/cli` 1.4.22, one minor line behind the core package; TM-U9 re-generates it with the CLI matching the core version. Better Auth calls this integration community-maintained and Fastify support beta ([integration](https://better-auth.com/docs/integrations/nestjs.md), no page date), and the package's peer range names `express` ^5, so Express is the adapter. Better Auth's Supabase migration guide copies bcrypt hashes into credential accounts with custom `hash` and `verify`, keeps user ids, and invalidates active sessions ([guide](https://better-auth.com/docs/guides/supabase-migration-guide.md), 2026-11-08).
- **Verified by S5:** behind the D5 rewrite on a scratch PostgreSQL 17.6: the schema from the CLI pushes, an anonymous call to a protected route is 401, a wrong password is 401, a `$2a$10$` bcrypt hash verifies and sign-in returns the same user id, the cookie is `HttpOnly` and `Lax` in the browser jar and reaches the protected route through the origin path, sign-out ends the session, and a foreign-origin POST is 403.
- **Rejected:** Better Auth in a Next.js route (the official integration, but it makes the Next server read the database and Auth, against Outcome 1, and puts auth state in Vercel Functions); Fastify (beta).
- **Reopens when:** the community package lags or breaks on a Nest or Better Auth minor and no fix lands. **Fallback that keeps the invariant:** mount Better Auth's own handler in NestJS without the community package, as Better Auth documents for Express: `toNodeHandler(auth)` on a catch-all route (`/api/auth/*splat` for Express v5) registered before any body parser ([Express integration](https://better-auth.com/docs/integrations/express.md), no page date), with a small Nest guard that reads the session through `auth.api.getSession`. It keeps auth in NestJS and Express. **Not spiked:** S5 ran the community package only. A move of Better Auth into a Next.js route would contradict Outcome 1, so it is not a fallback; it would go back to the Owner as an invariant change.
