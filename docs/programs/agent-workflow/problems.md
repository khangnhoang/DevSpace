### AW-P3: CLI-first tooling and repository-controlled delivery

- Status: Open (2026-10-31, Owner-grouped as one Medium task; implementation has not started).
- Problem: Agents select MCP before checking available CLI capabilities. GitHub CLI is behind the current stable release and Vercel CLI is not available in PATH; adding tools without an explicit delivery boundary also risks bypassing the repository's review, CI and release workflow.
- Evidence: H2-2a hosted catalog reads used the CLI successfully after MCP failures. The repository pins `supabase` to `2.121.0`; `gh --version` reports `2.96.0`, while the official latest release checked on 2026-10-31 is [2.103.3](https://github.com/cli/cli/releases/tag/v2.103.3); `Get-Command vercel -All` found no executable. The Owner grouped CLI setup, AW-P3 and the delivery restriction on 2026-10-31. Existing GitHub/Vercel integration remains the deployment path; permission ownership stays in `AGENTS.md` section 4.
- Direction: Deliver one coherent agent-workflow task: update the machine's GitHub CLI, install Vercel CLI globally, and align shared instructions and their direct consumers with CLI-first selection. Recheck official stable versions before installation; keep machine tooling outside application dependencies and record installation evidence alongside the repository change.
- Tool-selection boundary: Prefer the available CLI for supported operations (`npx supabase`, `gh`, `vercel`); check CLI help before declaring a capability missing. Use MCP only when the CLI lacks the required operation and MCP provides it. CLI errors, authentication failures or permission denials do not establish missing capability or authorize an MCP workaround; preserve role, target and permission boundaries.
- Delivery boundary: Encode the shared permission rule in `AGENTS.md` section 4 and link procedures to it. Tool availability grants no deployment authority. Agents follow the repository's delivery workflow with its existing separate grants; direct deployment, redeployment, promotion or rollback through CLI, MCP, API or UI outside that workflow requires an explicit Owner instruction naming the action and target. An authorized push/merge may trigger the existing automatic deployment, but a workflow description alone grants no push, merge or deployment permission.
- Exit condition: Resolved executable paths and installed versions are verified, permitted read-only CLI checks pass or remain explicitly blocked, and repository instructions consistently cover CLI-first selection and delivery authority. Bounded static decision cases cover supported CLI operations, confirmed CLI capability gaps, CLI/auth failures, inspection without deployment authority, workflow-triggered deployment, and an explicit Owner-directed deployment. Docs checks pass; machine setup evidence is distinguished from Git changes, and static cases are not claimed as live agent-compliance proof.

### AW-P4: Codex session handoffs lack a clear callback and receipt protocol

- Status: Open (2026-10-31, Owner-requested; covers implementation and both plan/diff review loops).
- Problem: Main repeatedly resumes after bounded `wait_threads` calls to inspect implementation or review progress. The workflow does not clearly distinguish waiting inside an active turn from ending the turn and resuming on a result message, leaving responsibility for result delivery and receipt unclear.
- Evidence: The Owner observed this during H2-2a. The current `wait_threads` contract waits for completion/attention with a timeout and returns compact progress on timeout; it does not document a durable subscription after Main ends its turn. `send_message_to_thread` provides follow-up messaging and `read_thread` exposes status/history, but their availability alone does not prove reliable callback delivery to an idle Main. The repository specifies independent sessions and Claude bindings, without a corresponding Codex callback/receipt procedure.
- Direction: Define the Codex planned-flow handoff: Main writes and self-reviews the plan, dispatches independent plan review, then ends its turn; the reviewer reports back and confirms receipt. After review PASS, Main presents the plan for Owner approval and separate commit/implementation grants, commits only when authorized, sends the approved plan or exact path/revision plus a brief to the implementor, then ends its turn. Implementation completion/blockers and independent implementation reviews use the same callback/receipt cycle; Main validates the actual candidate and routes corrections to the assigned session. No routine progress polling, per-checkpoint approval pause or premature implementation is introduced.
- Handoff content: Identify the task, plan revision/candidate commit, scope, role, allowed actions, verification, result destination and report expectations. Preserve human authorization for cross-thread messages in trusted context; an orchestrator's request alone is not authorization to message back. Bind each result and receipt to its particular handoff so an old message or unrelated active turn cannot count as acceptance.
- Receipt and ownership: Before reporting completion, the implementor finishes authorized writes/checks/commits and performs no further checkout writes while awaiting receipt; reviewers remain read-only. The recipient acknowledges the matching result before waiting for the sender to stop, avoiding circular waits. Prefer an explicit receipt or correlated turn-start/completion evidence over a transient `active` status; a fast completed receiver must also count. Receipt is not review PASS or a new work grant, and does not itself require another receipt. Ending a turn does not close or archive the reusable session; existing single-writer rules still apply.
- Dispatch/stop race: A reviewer or implementor may return an unexpected blocker immediately, before, during or just after Main ends its dispatch turn. Verify each boundary: the report remains retrievable and is either handled by the current turn or queued to trigger a subsequent turn, with a matching receipt and no duplicate dispatch. A successful send, a saved message or an unrelated active Main alone does not prove handling; an ACK detects receipt but cannot itself guarantee wake-up. If delivery or receipt times out, retain the report and expose an unresolved handoff rather than claiming Main took over or silently retrying the work.
- Feasibility boundary: Before adopting this as the operating procedure, verify the installed runtime with bounded, Owner-authorized message-only probes for idle-Main wake-up, message/receipt correlation, busy/queued delivery, fast receiver completion and failed or timed-out delivery. Do not claim the wake-up/receipt guarantee from documentation or tool success alone. Missing callback capability remains an explicit blocker; do not silently substitute perpetual polling, scheduling or a new orchestration service. Shared lifecycle belongs to `docs/agent-loops.md`, permissions to `AGENTS.md`, and Codex-specific tool bindings must remain separate from Claude-only bindings.
- Exit condition: The documented procedure covers plan review, implementation, diff review and correction loops; the bounded runtime probes demonstrate result delivery and receipt after Main has ended its turn, with visible failure handling and no duplicate work or concurrent checkout writers. Docs checks and instruction review pass; unverified runtime behavior remains explicitly pending rather than being reported as solved.
