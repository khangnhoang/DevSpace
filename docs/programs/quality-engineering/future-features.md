## QE-F2: Automate representative failure paths and concurrency invariants

- Status: Recorded; QE-F1 safe-fixture support was delivered in PR #42, and this item remains deferred until its own initiative is approved; transferred from BL-F7 on 2026-10-30.
- Direction: select concrete regression-worthy cases during discovery, using existing Vitest, real local database and Playwright/API helpers rather than adding a new test framework. Extend the E2E fixture to permit only explicitly expected request/status failures per test, with assertions for recovery and unchanged/persisted data; unexpected 5xx responses and external/hosted network access must still fail. Distinguish sequential retries, stale tabs and genuinely competing requests: the payment H2/K6 rows do not prove concurrent integrity. For relevant counters, reservations or state transitions, use independent requests/connections, identify the shared resource and assert the final invariant; use controlled synchronization when needed rather than claiming `Promise.all` guarantees a race. Keep normal user-flow wiring in browser E2E and endpoint/DB guarantees in integration tests where sufficient. Do not mock authorization or the database guarantee being tested. Use the existing known-bug contract for approved unresolved P5/P6/P25 cases; this entry does not authorize their product fixes. Keep real mail delivery/provider quality separate from application-side success/failure handling. Coordinate with BL-F2 and app-foundation coverage instead of duplicating those UI scenarios; no rewrite of the entire suite or blanket load/visual testing.
- Target program: quality-engineering.

## QE-F7: Classify tests by layer, then by area

- Status: Recorded 2026-11-04 by the Owner; deferred until its own initiative is approved.
- Direction:
  - Today `__tests__/` has three flat top folders named after Vitest projects or the Playwright suite (`unit`, `rls`, `e2e`) and no rule below them. About half of `unit/` tests the test tooling, not the app (`test-stack-*`, `server-guard`, `e2e-env`, `local-stack`, `known-bug`, `monaco-copy`, `docs-only`). `rls/` is really the integration layer: it also holds RPC (`is_admin`, `[P11]`), Auth (`[P13]` in `profiles.test.ts`) and tooling tests (`fixture-ownership`, `setup`, `e2e-preflight`). `e2e/` mixes specs with harness files.
  - Target: layers first, `unit` (with `unit/components/` from QE-F8), `integration` (today's `rls`) and `e2e`, plus a separate branch for tests of the test tooling. Below a layer, unit tests follow the source path (`unit/lib/schemas/...`, `unit/app/admin/lessons/...`) and integration tests follow the app area (profiles, content, coupons...), not the mechanism (RLS, RPC, Auth), so one area's guarantees stay together. No empty category folders.
  - Migrate gradually: new tests follow the rule at once; an existing file moves when a task touches it. Renaming `rls` touches `vitest.config.mts`, the rls global setup, `npm test`, CI and `test-quality-strategy`, so it is an initiative of its own. The techstack migration (ADR 0001) rewrites most Supabase integration tests, so do not reshape them more than the rule needs.
- Target program: quality-engineering.

## QE-F8: Component tests for client components under `unit/components/`

- Status: Open. First step done in [QE-U4](implementation-plans/qe-u4-component-tests/plan.md) (Owner, 2026-11-04): the `components` project, `CourseFormDialog` tests, the e2e rule in `test-quality-strategy` and the move of C2 (`C2 -> __tests__/unit/components/CourseFormDialog.test.tsx`). The entry is not closed by QE-U4; it closes only when every e2e spec is audited and every client-only row is moved or kept with a recorded reason.
- Direction:
  - Add Testing Library and a DOM environment (`jsdom` or `happy-dom`) for client-component logic: field errors and `aria-invalid`, an error clearing after a fix, no request for an invalid form, disabled states, the duplicate-submit guard (a deferred save submitted twice is called once). Files sit under `unit/components/` in their own Vitest project with the DOM environment and setup; `npm run test:unit` runs it with the rest of `unit`, with no Docker. New packages need the Owner's grant (`dependency-updates`).
  - Limits: Vitest renders synchronous Server and Client Components but not `async` Server Components (Next.js Vitest guide), so data-loading `page.tsx` files stay in e2e. jsdom has no layout engine: Radix `AlertDialog` usually works, `Select` needs polyfills, and anything that depends on size, position or focus geometry stays in the browser. Action and Supabase calls are replaced at a boundary (a save passed as a parameter, as `saveAiExercises` does); the behavior under test is never mocked. Component tests do not replace RLS, server-action or persistence checks, nor the visual review.
  - Open follow-up (the audit): read every spec in `__tests__/e2e/`, classify each row as an integration boundary or client-only, move client-only assertions to component tests form by form under the e2e rule of `test-quality-strategy`, delete redundant rows with a recorded mapping per moved row, and measure the e2e time under QE-F3. Extend to other forms only once the component layer runs fast and stable. QE-U4 did the tooling and `CourseFormDialog` only (C2 moved; C1, C3, C4, C5 and D1 stay, each an integration boundary or layout row).
  - Audit (QE-U6, 2026-11-07): every one of the 164 test-defining rows in the 11 specs (`test(` and the nine `recoveryTest(` rows of `auth-forms.spec.ts`) is classified in its spec's header (`Layer audit`) as an integration boundary or as client-only with the component test file it would move to. 28 rows are client-only; the other 136 need persistence, a refusal, a failed request, permission, redirect, upload or real-browser layout. Client-only rows per spec: `admin-content-forms` 9 (D1 x4, H2, L2, E2, E5, E6; D1 of the course dialog is already covered by `CourseFormDialog.test.tsx`), `auth-forms` 8 (AU2, AU6, AU9 x4, AU4, AU10), `admin` 3 (A1 chapters card, A9, A12), `learner-forms` 3 (F3, F5, F8), `payment-admin` 2 (AP4, AP5), `learner` 1 (L7), `public` 1 (S6), `student` 1 (T3); `action-validation`, `admin-user-forms` and `payment-learner` have none. Some boundary rows also hold a client-only part (a duplicate-submit guard in F4 and F7, the cancel paths of A4 to A8, the filter logic behind T6 and T8). The audit moved no row: each move needs a component test, its mutation proof and a recorded mapping, form by form. The entry stays open for those moves.
  - Moving e2e rows: a row whose assertions are client-only moves to a component test and the e2e row is deleted, form by form when a task touches it. Each form keeps at least one successful and one rejected e2e row proving the wiring (action, persistence, server refusal, permission, upload). Before deleting a row, show the replacement fails when the logic is broken, and record the mapping (for example `C2 -> unit/components/CourseFormDialog.test.tsx`). This changes the app-foundation minimum of field-level e2e rows, so the Owner approves the rule change in `test-quality-strategy` and the app-foundation master plan first. Most e2e time is likely fixed cost (build, stack, browser); measure any saving under QE-F3 rather than promising one.
- Target program: quality-engineering.
