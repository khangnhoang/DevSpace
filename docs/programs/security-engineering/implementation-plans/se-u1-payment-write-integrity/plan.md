# SE-U1 detail plan — Coupon and payment write integrity

Revision: r3, 2026-11-07. Owner approval: 2026-11-07; current authority lives in [progress.md](../../progress.md). Charter: [security-engineering](../../README.md). Starts from the H2-2b scope and reservation design of security-hotfix [plan-h2.md](../../../security-hotfix/plan-h2.md) (D1, B12, B13, P25), revised here against today's code and hosted catalog.

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: every payment and coupon-usage change goes through one database function per transition, so a coupon use is reserved when a code is applied and released when the order is cancelled, rejected, switched to another code or deleted while pending, approval and rejection act only on a pending order, approval and its enrollment commit together, and a learner who already owns the course, or asks for a free course, gets no pending order. SE-P8 to SE-P12 are resolved by this initiative.

| ID | Observable result |
| --- | --- |
| AC1 | A learner who applies an active code with uses left to their own pending order gets the discounted amount (course price × (100 − percent) / 100, rounded, clamped to 0..price); the order stores the coupon and its amount, and the coupon's `used_count` rises by exactly 1. |
| AC2 | Applying the same code again to the same order changes no count. Switching the order to another valid code reserves one use of the new code and releases the old one in the same transaction. A refused apply (unknown, inactive or exhausted code, another user's order, an order that is not pending) changes no count, no amount and no stored coupon, and returns today's messages ("Mã giảm giá không tồn tại hoặc đã hết hạn", "Mã này đã hết lượt sử dụng", "Đơn hàng không hợp lệ"). |
| AC3 | A code with `max_uses` set is never reserved beyond `max_uses`, including when two orders apply its last use at the same moment: exactly one succeeds and the other gets "Mã này đã hết lượt sử dụng". A code with `max_uses` null is unlimited on every path (SE-P12). |
| AC4 | The learner cancelling their pending order, or an admin rejecting it, sets it `failed` and releases its reserved use, if any. Cancelling another user's order, or any order that is not pending, changes nothing and returns "Không thể hủy giao dịch này"; the payment modal shows that error instead of "Đã hủy giao dịch". |
| AC5 | An admin approving a pending order sets it `success` and creates the learner's enrollment in one transaction: an existing enrollment is kept without a duplicate error, and a failed enrollment write leaves the order pending. The reserved use stays counted. Only the request that wins the transition attempts the approval mail, once, after the commit; a mail that fails (resolved failure or thrown error) leaves the approval in place, is logged on the server, and the action still reports the approval. Delivery itself is not guaranteed (no outbox). |
| AC6 | Approving or rejecting an order that is not pending (already approved, rejected, cancelled, or unknown) changes nothing, sends no mail and returns "Đơn đã được xử lý". When an approval and a cancel or reject race on the same order, exactly one wins; if the approval wins, the enrollment exists. |
| AC7 | `createPendingPayment` never discounts: it creates a pending order at the course price with no coupon, or returns the caller's existing pending order for that course (`isResumed: true`). A signed-in learner already enrolled in the course gets "Bạn đã sở hữu khóa học này", a free course (price 0) gets "Khóa học này miễn phí, hãy đăng ký trực tiếp", an unknown course keeps "Khóa học không tồn tại"; none of these writes a row (SE-P11, D3). This holds when the create races an approval of the learner's earlier order: no pending order exists once the enrollment does. |
| AC8 | At most one pending order exists per user and course, even under two simultaneous create requests (D4). |
| AC9 | Every payment action parses its arguments with a schema from `lib/schemas/` before any read or write; a malformed argument returns the action's failure shape with the generic parse message and writes nothing. The auth, ownership and admin checks of today stay inside the actions. |
| AC10 | No client (anon, a learner, an admin session) can execute the payment functions through the API. From M1 on, a direct write to `payments` by any role but the functions' owner is refused when it inserts anything but a plain pending order at the course price without a coupon, sets `status`, `amount` or `coupon_id` on an order that is not pending (even to the value it already has, as the old approve re-sets `success`), or touches an order that holds a coupon or sets one; the old code's normal paths on orders without a coupon keep working until the deploy. After M2, the service role, anon and authenticated cannot insert or update `payments` at all. |
| AC11 | Deleting a pending order that holds a use, directly or through deleting its course or its user, releases that use, also when two such deletes run at once over the same coupons in opposite order. Deleting a `success` order keeps its use counted: a consumed use stays consumed (D6). |
| AC12 | Each migration has a rollback that restores its earlier catalog exactly. M1's rollback refuses to run while any pending order holds a coupon, so no reservation loses its link; the runbook clears them first. SE-P8 to SE-P12 stay open until both migrations are applied on hosted, the postflights pass and the Owner confirms production QA. |

### 1.2 Scope and non-goals

- In scope: migration M1 (`coupon_id` on `payments`, the partial unique index of pending orders, four `security definer` payment functions, the transition guard and the delete release triggers) and M2 (revoke direct `payments` writes), each with a rollback; the rewrite of `app/action/payment.ts` onto the functions with Zod schemas in `lib/schemas/`; the cancel feedback in `CoursePaymentModal.tsx`; database, unit, endpoint and browser tests, turning known bugs K4 to K8 into normal rows; the hosted runbook. Two PRs (D2): PR 1 on `fix/se-u1-payment-write-integrity` carries M1, the code and its tests; PR 2 on `fix/se-u1-payment-write-lock`, stacked on PR 1's last commit, carries M2 and its tests and is opened after PR 1 is merged.
- Non-goals: automatic expiry of abandoned pending orders (an admin rejects stale orders to free their uses, as plan-h2 accepted); coupon admin UI, coupon dates, a `discount_percent` or `used_count` constraint; payment states beyond `pending`, `success`, `failed`; revoking the service role's `coupons` writes (the e2e fixture restores `used_count` with it); a mail outbox or retry; BL-P17 and BL-P18 on `/admin/transactions` (a Codex-gated item does not batch with backlog items); notifications for a paid enrollment; the QR, transfer text or modal design; the reviews and comments parts of plan-h2 (done in H2-2a and SE-U4).
- Unchanged: published migrations, every RLS policy, `enrollCourse`, `deleteCourse`, `deleteUserAccount`, `getAllPayments`, the admin dashboard reads, the transactions page except that its existing toasts now show the new messages.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. Each payment function is `security definer`, owned by `postgres`, `set search_path = ''`, schema-qualifies every object, revokes `execute` from `public, anon, authenticated` and grants it to `service_role` only. The actions pass the user id from `requireUser()`, never from the client. | A client calls the function through REST, or a hijacked `search_path` resolves another object. |
| G2. Each transition is one conditional write on the expected state (`where status = 'pending'`, with the owner where the learner acts) whose row count decides the result. Lock order: the transaction-level advisory lock of (user, course) first, where taken, then the payment row, then coupon rows in ascending id order. `create_pending_payment` and `approve_payment` both take that advisory lock before their checks and writes, and create checks enrollment only after taking it. | A double approval mails twice, a use is released twice, two code switches deadlock, or a create slips a new pending order in after an approval. |
| G3. The reservation is `update coupons set used_count = coalesce(used_count, 0) + 1 where id = … and is_active and (max_uses is null or coalesce(used_count, 0) < max_uses)`; a release is `greatest(coalesce(used_count, 0) - 1, 0)`; no external call or mail inside a function or trigger. | The last use is sold twice, a null `used_count` reads as exhausted, or a lock is held across a mail. |
| G4. The guard trigger is `security invoker` and decides by `current_user`: the payment functions run as their owner and pass; every other role (service_role, authenticated, anon) is held to AC10. The guard has two `before update` triggers: one without a column list refuses any direct update of an order that holds a coupon (including one that sets only `user_id`, `course_id` or `updated_at`), and one `before update of status, amount, coupon_id` catches a same-value assignment on a non-pending order. The delete release trigger is `security definer` and statement-level (`referencing old table`): it groups the deleted pending coupon orders by coupon and releases them in ascending coupon id, one update per coupon, so concurrent deletes lock coupons in the same order. Neither trigger reads a client-settable setting. | Old or stale code re-approves and mails again, desyncs a reservation, a cascade delete leaves a use counted, or two cascades deadlock. |
| G5. The actions call no other payment or coupon write; `increment_coupon_usage` and every direct `payments` insert/update leave `app/action/payment.ts`. CP2 greps `app` and `lib` for `.from("payments")` writes and `increment_coupon_usage`. | A leftover path desyncs `used_count` or fails only on production. |
| G6. M1 is applied on hosted from PR 1's head, which contains no M2; after that apply M1 and its rollback are frozen, and a fix is a new migration. A correction to PR 1 after PR 2's branch was cut is carried into PR 2 (with the Owner's grant for that git action) before PR 2's review and CI. | `db push` applies M2 before the code is live, hosted runs a different M1 than the repository, or PR 2 is tested against a stale PR 1. |
| G7. Tests write only through the managed runners. The functions are callable only by the service role, so their own tests call them as `service_role` (REST with the service key, or `withPg` with `set local role service_role`); this is the one exception to "service role never sends the request under test", and actor checks stay at the action endpoints (`callAction`). Concurrency rows use two independent `withPg` connections with a held lock and a `pg_locks` wait check, not `Promise.all` alone. Guard rows that expect a direct `service_role` write to succeed run in a `withPg` transaction that grants `insert, update` on `payments` to `service_role` (a no-op before M2), then `set local role service_role`, and roll back; outside such a transaction the suite asserts the state of the migrations present. The guard is never tested as `postgres`. Every order and coupon a test creates is recorded and removed; the end-of-run audit stays clean. | A race test that never overlaps, residue in `payments`/`coupons`, or a function test that silently runs as a superuser. |
| G8. Main supplies hosted metadata; the implementor never reaches hosted. | A hosted write outside the grants. |

### 1.4 Owner decisions that bind this unit

- D1 (security-hotfix plan-h2, 2026-10-22): a use is reserved when a code is applied and released on cancel, reject or switch; `max_uses` is a hard limit; null means unlimited.
- D2 (2026-11-07): two migrations. M1 is additive for the old code's normal paths and applied before PR 1 merges; M2 revokes direct `payments` writes and is applied only after PR 1's production deploy is live. No window in which the normal payment actions fail. Between M1 and the deploy, a code applied by the old code is not counted, as today; between the deploy and M2, the M1 guard refuses old or stale code on orders that hold a coupon (AC10), and a stale old discount on an order without a coupon stays uncounted, as today.
- D3 (2026-11-07): a direct `createPendingPayment` for a free course is refused and creates no order.
- D4 (2026-11-07): a partial unique index keeps at most one pending order per user and course; if hosted already holds duplicates, M1 aborts and Main reports to the Owner.
- D5: hosted behavior probes (simulated roles inside a rolled-back transaction, on users, courses and coupons the Owner names) need a separate Owner grant at the gate where they run; until granted, that gate stays `pending`, and SE-P8 to SE-P12 do not close. Catalog postflight needs no further grant. This plan grants no implementation, commit, push, PR, merge or hosted action.
- D6 (2026-11-07, approved with r3): deleting a `success` order does not give its coupon use back; only pending orders release. Counter checks therefore assert the expected delta of each scenario, not a global equality with the orders that still exist.

## 3. Bounded implementation hypotheses

- M1 `se_u1_payment_rpcs`, in one transaction: `alter table public.payments add column coupon_id bigint references public.coupons(id) on delete restrict` (nullable, no backfill: older orders reserved nothing); `create unique index payments_one_pending_per_user_course on public.payments (user_id, course_id) where status = 'pending'`; functions returning `jsonb`:
  - `create_pending_payment(p_user_id uuid, p_course_id bigint)`: unknown or null-price course → `invalid_course`; price 0 → `free_course`; then the advisory lock; enrolled → `enrolled`; existing pending → `resumed`; else insert → `created`.
  - `apply_payment_coupon(p_payment_id bigint, p_user_id uuid, p_code text)`: plan-h2's function with G2/G3, `upper(btrim(p_code))`, the amount clamped to 0..price, results `invalid_payment`, `invalid_coupon`, `coupon_exhausted` or `{amount, discount_percent}`.
  - `close_pending_payment(p_payment_id bigint, p_user_id uuid)`: null user means admin reject; returns whether a row changed and releases its coupon.
  - `approve_payment(p_payment_id bigint)`: reads the order's user and course, takes the advisory lock, conditional update, enrollment `on conflict do nothing`; `{approved, user_id, course_id}`.
  - `payments_guard` (before insert, before update) and `payments_release_on_delete` (after delete) as in G4.
- M2 `se_u1_payment_write_lock`: `revoke insert, update on public.payments from service_role, anon, authenticated`; DELETE stays (test cleanup, cascades). Rollbacks: M2 grants them back; M1 aborts if a pending order holds a coupon, else drops the triggers, functions, index and column.
- `lib/schemas/payment.ts`: `paymentIdSchema` (positive int), `couponCodeSchema` (trimmed, non-empty, bounded length, upper-cased); `createPendingPayment` reuses `courseIdSchema` and drops its `couponCode` parameter; a null `cancelPayment` id may keep its current message or take the generic parse message.
- `app/action/payment.ts`: each action parses, authenticates, calls its function and maps results to the messages of section 1.1; `approvePayment` mails only for `approved: true`, using the returned ids, and treats a resolved `success: false` or a thrown mail error as logged-only.
- `CoursePaymentModal.tsx`: `handleCancelPayment` shows `res.error` and does not report a cancel that failed.
- Tests: a new `__tests__/rls/payments.test.ts` with a test-plan header; e2e K4–K8 become normal rows and new H/AP rows cover AC2, AC4, AC6, AC7; `action-validation.spec.ts` gains payment parse rows; unit tests for the schemas and the action boundaries (mail resolved failure and rejection: approval reported, approve function called once); `fixture-ownership.test.ts` inserts its payment through `withPg` as the table owner.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| R1. Hosted holds duplicate pending orders, so M1's index fails. | The whole M1 transaction aborts (D4); Main reports, and the Owner rejects the extra orders before a new attempt. |
| R2. Two code versions run at once: before the deploy old code applies codes uncounted; after it, a stale tab or the old deployment URL can still call old actions until M2. | D2 accepts uncounted old discounts on orders without a coupon; the M1 guard refuses every old write on an order that holds a coupon, every non-pending status change and every discounted insert (AC10), so no reservation is lost; M2 follows the deploy promptly. |
| R3. M2 lands while some code still writes `payments` directly. | G5 grep; M2 only after the deploy is live; full e2e on the locked table in CP3; postflight checks the functions still write. |
| R4. An abandoned pending order holds its use until someone cancels or rejects it. | Accepted in plan-h2; admins reject stale orders. Recorded as a known limit, not fixed here. |
| R5. Existing hosted `used_count` values include uses never tied to an order, and deleted `success` orders keep their uses (D6), so `used_count` cannot be recomputed from existing orders. | Postflight checks only that `used_count` ≥ the coupon's pending plus success orders and records the per-coupon figures, under the D5 grant; tests assert per-scenario deltas. |
| R7. A statement that deletes several courses or users at once releases in several internal statements, which can still deadlock against another such statement. | The app deletes one course or one user per request; a deadlock rolls the whole delete back without a partial count, and the admin retries. Recorded as a known limit. |
| R6. A Next update or harness limit prevents a concurrency or mail row. | Report the blocker with the missing guarantee before proceeding (`test-quality-strategy`); never replace it with a sequential check. |

- Rollout runbook: (1) PR 1 CI green and Codex implementation PASS on both branches; (2) Main preflight, read-only: hosted catalog matches section 2; (3) prepare grant: from PR 1's head with a clean tree, `db push --linked --dry-run` lists exactly M1; (4) apply grant: apply M1; (5) M1 postflight before the merge: catalog (functions, ACLs, triggers, index, column) by Main; behavior probes under the D5 grant, as `service_role` in one rolled-back transaction on the named user, paid course and coupon: create, apply, switch, cancel and approve with their counts, guard refusals, delete release; anon and authenticated `rpc` refused; (6) merge grant for PR 1, then Main confirms the production deploy is live; (7) open PR 2 (its own push and PR grants), CI green; (8) prepare and apply grants for M2 from PR 2's head; (9) M2 postflight: catalog privileges by Main; under the D5 grant, direct `service_role` insert/update refused and the functions still write, rolled back; (10) merge grant for PR 2; (11) Owner QA; SE-P8 to SE-P12 close only after (5), (9) and (11) passed.
- Stop when: hosted metadata differs from section 2, a dry run lists anything else, a postflight check fails, or a probe lacks its grant (that gate stays pending).
- Rollback: (a) M2's `.down.sql` restores the grants; (b) revoke `execute` on `apply_payment_coupon` from `service_role` so no new reservation starts, and confirm in `pg_stat_activity` that no call is running; (c) an admin approves or rejects every pending order that holds a coupon through the functions; (d) Main records the per-coupon figures of R5 (read grant); (e) revert PR 1's code; (f) M1's `.down.sql`, which refuses while a reserved pending order remains. Afterwards D1 is no longer enforced and the `coupon_id` history of closed orders is dropped; the Owner accepts both when choosing to roll back.
