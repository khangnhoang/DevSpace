# SE-U4 detail plan — Comment write integrity and avatar path ownership

Revision: r3, 2026-11-07 (r1 independent review: 5 Required fixed in r2; r2 Codex round 1: 3 Required fixed in r3). Owner approval: 2026-11-07; current authority lives in [progress.md](../../progress.md). Charter: [security-engineering](../../README.md).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: soft-deleted comments are no longer readable or writable through the API by any application role, only enrolled learners of the lesson's course or admins can create comments, and a signed-in non-admin can write `avatars` objects only under their own user-id folder.

| ID | Observable result |
| --- | --- |
| AC1 | No row whose `deleted_at` is set is returned to anon or to any signed-in actor, including the comment's owner and an admin, through any read path the API exposes for `comments` (list by lesson, by id, by user, any filter). Non-deleted comments stay readable by everyone, as today. |
| AC2 | The stored `content` and `deleted_at` of a soft-deleted comment are kept unchanged in the database; nothing overwrites, purges or moves them. Comments already soft-deleted before the migration become hidden by the same rule without any data change. |
| AC3 | The owner can still soft-delete their own non-deleted comment from the `/learn` comment panel; the comment then disappears from the list and stays gone after a page reload, and the stored row keeps its content with `deleted_at` set. An admin keeps the existing API ability to soft-delete another user's comment (no admin UI exists for it). Another non-admin user and anon cannot soft-delete someone else's comment, and nothing changes. |
| AC4 | No application role can read, edit, restore or re-delete a soft-deleted comment through the API, whether or not the request filters on table columns; no new management, restore or purge feature is added. |
| AC5 | A signed-in user can INSERT a comment as themself only on a lesson whose course they are enrolled in, and only as a non-deleted comment; an admin can comment on any lesson. A user who is not enrolled (free or paid course alike), a forged `user_id`, an insert with `deleted_at` set, and anon are refused and nothing is written. |
| AC6 | The enrolled student and the admin keep listing, adding and editing non-deleted comments in the `/learn` panel as today. |
| AC7 | A signed-in non-admin can upload to `avatars` only at a path whose first folder is their own user id, and cannot upload to another user's folder or to a flat (folder-less) path. An admin can still upload to any path in `avatars` (avatars of other users and course images). Anon cannot upload. Write access to every other bucket is unchanged. |
| AC8 | A signed-in non-admin can update or move only objects they own inside their own folder, and cannot rename or move any object into another user's folder or out of their folder. An admin can update any `avatars` object. Public read of `avatars` is unchanged. |
| AC9 | The learner profile save uploads the new avatar to `<own user id>/…` and the profile then shows it, the admin user dialog keeps uploading avatars, and admin course image upload keeps working. Existing flat-path objects and their public URLs keep working. |
| AC10 | Each migration has a rollback that restores its previous policies and objects exactly; no data is lost either way. SE-P4 and SE-P5 stay open until this PR is delivered and its hosted acceptance passes. |

### 1.2 Scope and non-goals

- In scope: one PR on `fix/se-u4-comment-avatar-integrity` with two checkpoints and two migration/rollback pairs: M1 comment integrity (SE-P4), M2 avatar path ownership (SE-P5); a narrow soft-delete function and the switch of `deleteComment` to it; the learner avatar path change in `lib/supabase.ts`; RLS, Storage and browser regressions and the test-helper changes they need; hosted preflight/postflight runbook.
- Non-goals: restricting reads of non-deleted comments to enrolled users (D2); an admin view, restore, purge or moderation feature for deleted comments; overwriting or deleting stored comment content; an enrollment check on comment UPDATE (an owner can still edit or soft-delete their own earlier non-deleted comment); new comment UI or copy beyond removing what the change makes unreachable; the admin user-create avatar order (SE-P22); a separate bucket for course images; moving or deleting existing flat-path objects; a Storage DELETE policy; avatar type or size rules; SE-P21; H2-2b; dependency updates.
- Unchanged: published migrations, `handle_new_user`, `prevent_comment_reassign`, `update_comments_updated_at`, grants on `comments`, the public SELECT policy of `avatars`, other buckets, and Storage-managed objects except the two named `avatars` write policies.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. Enforce AC1, AC4 and AC5 in the database (RLS), not in `lib/supabase.ts` or the UI, with no `is_admin()` exemption for reading or writing deleted rows. | A direct REST call, or an admin session, still reads or changes a deleted comment. |
| G2. Drop each replaced policy by its exact hosted name before creating its successor. After M1 `comments` has exactly one SELECT, one INSERT and one UPDATE policy; the SELECT `USING`, the INSERT `WITH CHECK` and the UPDATE `USING` all contain `deleted_at is null`, the UPDATE keeps H2-2a's `WITH CHECK`. CP1 asserts the exact policy list and expressions from the catalog. | An old permissive policy is OR-ed in, or an UPDATE that references no column restores a deleted row through the UPDATE policy alone. |
| G3. Before switching `deleteComment`, a local test shows the current direct soft delete fails once deleted rows are hidden; the replacement is one function that soft-deletes a single non-deleted comment for its owner or an admin and nothing else. | Soft delete silently breaks, or a broader mechanism (service-role action, generic RPC, restore path) is added. |
| G4. The function is `security definer` (a security-invoker function hits the same SELECT check), owned by `postgres`, with `set search_path = ''`; it runs one statement `update public.comments set deleted_at = now() where id = $1 and deleted_at is null and (user_id = auth.uid() or public.is_admin()) returning …` and returns only whether a row changed; `execute` is revoked from `public` and `anon` and granted to `authenticated` (no `anon` or `public` execute). | The function becomes a bypass that deletes other users' comments, works for anon, races, or resolves a hijacked object. |
| G5. Every new Storage policy expression starts with `bucket_id = 'avatars' and (…)`; the UPDATE policy has an explicit `WITH CHECK` on the new path, not only `USING` on the old row. CP2 asserts the exact policy expressions from the catalog. | Writes open in every bucket, or an owner moves their object into another user's folder. |
| G6. Tests write only through the managed test runner; every comment and Storage object a test creates is recorded by exact identity (for a move, the source and destination names before the request), removed in `finally` and verified absent by an exact-name read, not a root listing; the end-of-run audit stays clean. A hidden-row test proves the row exists (service-role read-back) before asserting it is not returned. A probe that could change a seed row runs inside a rolled-back `withPg` transaction. | Residue in `comments`/`storage.objects`, an absence check that cannot fail, a changed seed row, or an empty result that passes because the row never existed. |
| G7. Main supplies hosted metadata; the implementor never reaches hosted. | A hosted write happens outside the grants. |

### 1.4 Owner decisions that bind this unit

- D1 (2026-11-06): SE-P4 and SE-P5 are one initiative, one PR, two checkpoints with separate migration/rollback pairs; a blocker in either holds the whole PR. This is a task-specific exception to the planning skill's generic batch exclusion, as for SE-U3 D6.
- D2 (2026-11-06): reads of non-deleted comments stay public; only writing a new comment requires enrollment in the lesson's course, or admin, for every course including free ones.
- D3 (2026-11-06, revised the same day): soft-deleted comments are hidden through the API from every application role, admin included; their content stays in the database and is not overwritten. Review the existing policies so no other policy exposes deleted rows; check and adjust `deleteComment` so soft delete keeps working; add no management or restore feature.
- D4 (2026-11-06): a non-admin writes avatars only under `<uid>/…`; an admin writes any path in `avatars`; existing flat objects stay.
- D5 (2026-11-07): rollout applies M1 and M2 together right after the production deploy of the merge is live, accepting a short window in which production soft delete fails because the function does not exist yet; learner avatar upload keeps working through that window. The Owner also accepts that a browser tab opened before the deploy keeps the old bundle, so after the apply its comment delete and learner avatar upload fail until the page is reloaded; no data is lost.
- D8 (2026-11-07): Main runs the catalog postflight without a further grant. Behavior probes on hosted (deleted-row visibility, INSERT rules, the function) read user rows and write inside a rolled-back transaction, so they need a separate Owner grant at that time, naming the accounts and rows; until granted they stay `pending`, and SE-P4 and SE-P5 do not close.
- D6 (2026-11-07): the Owner confirmed SE-U3 hosted acceptance and production QA; SE-U3 is completed, so SE-U4 is the only open initiative.
- D9: charter decisions and ADR 0007 own the pre-migration boundary. This plan grants no implementation, commit, push, PR, merge or hosted action.

## 2. Repository facts

Baseline: `e76cc05f4a38f682520cb88cb6bf0fa80840b44c` (main after PR #69), checked 2026-11-06/07. Hosted metadata: Main's read-only catalog queries of 2026-11-06/07.

- `comments` has `content` with `comments_content_check` and nullable `deleted_at`. Policies, identical on hosted: "Public view ALL comments" (SELECT, `public`, `true`), "Authenticated users can comment" (INSERT, authenticated, `auth.uid() = user_id`), "Owners and Admins can update/soft-delete comments" (UPDATE, owner or admin `USING`, H2-2a `WITH CHECK`); no DELETE policy. Triggers `comments_prevent_reassign`, `update_comments_updated_at`. anon and authenticated hold table-level `ALL` — AC1, AC4, AC5, G2.
- Hosted has no view, rule, non-system function body or publication referencing `comments`; `pg_graphql` was removed by SE-U3. No server code reads `comments` with the service role; only test helpers do — AC1.
- `getCommentByLesson` selects every row of a lesson including `deleted_at`; `deleteComment` updates `deleted_at` filtered by `id` and `user_id` and reads back `id`; under a SELECT policy that hides the new row, PostgreSQL refuses that update — G3, G4. `LessonComments.tsx` reloads the list after a delete and renders "Bình luận đã bị xóa" for rows with `deleted_at` — AC3.
- `/learn` is gated by `requireCourseAccess` (enrolled or admin), so the only UI caller of `addComment` is enrolled or admin — AC5. No admin UI deletes another user's comment — AC3.
- Seed: course 1 free (lessons 1–2), course 2 paid (lessons 3–4); `student` enrolled in course 2, `learner` and `admin` enrolled nowhere; comment 1 by `student` on lesson 3 — AC5 tests.
- Storage: bucket `avatars` public, 2 MB, `image/*`. Policies, identical on hosted, all to `public`: "Avatar xem cong khai" (SELECT), "User tu upload avatar" (INSERT, `bucket_id = 'avatars' and auth.role() = 'authenticated'`), "User tu sua avatar" (UPDATE, `bucket_id = 'avatars' and auth.uid() = owner`, no `WITH CHECK`) — AC7, AC8, G5.
- Hosted `storage.objects` is owned by `supabase_storage_admin`; `postgres` is neither owner nor member nor superuser, but hosted `supautils.policy_grants` lists `storage.objects` for `postgres`, which lets the migration role create, alter and drop its policies — M2 is appliable with `db push`.
- Writers to `avatars` in `lib/supabase.ts`: `uploadUserAvatar` (flat `avatar_<ts>_<name>`, used by the learner `updateProfile` and by the admin `editUser`/`UserFormDialog`), `updateCourse` (`course_<id>_<ts>`) and `addCourse` (`course_new_<ts>`), all with the caller's browser session and plain upload — AC7, AC9. Next image patterns already allow nested avatar paths.
- Tests the change touches: `__tests__/rls/community.test.ts` [R3]–[R14] ([R5]: admin soft-deletes another user's comment through REST); `__tests__/e2e/student.spec.ts` [T4] deletes a comment and asserts "Bình luận đã bị xóa" is shown; `__tests__/e2e/service-role.ts` `avatarObjectNames()` lists only the bucket root and `removeAvatarObject` checks absence with it; `learner-forms.spec.ts` [F9] (`objectsBefore` equality), [F10] (flat-name matcher) and [F12] (real upload, flat-name matcher, `toContain` on the root listing); `admin-user-forms.spec.ts` fakes uploads and asserts the flat admin name; `UserFormDialog.test.tsx` mocks `uploadUserAvatar`. No rls test covers Storage yet. The rls project cannot import the browser client in `lib/supabase.ts`.

## 3. Bounded implementation hypotheses

- M1 `se_u4_comment_integrity`: replace "Public view ALL comments" with a SELECT policy `deleted_at is null` for `public`; replace the INSERT policy with `user_id = (select auth.uid()) and deleted_at is null and (enrolled in the lesson's course through `lessons` and `enrollments`, or public.is_admin())`, like `exercises_select_enrolled_or_admin`; alter the UPDATE policy's `USING` to add `deleted_at is null`, keeping its `WITH CHECK`; add `public.soft_delete_comment(comment_id bigint)` as in G4. A migration comment records that deleted comments are hidden from admins too (D3).
- `deleteComment` calls the function and keeps its return contract (null on success, an error, or the existing not-found message when no row changed); its now-unused `userId` parameter may be dropped together with its one caller.
- `LessonComments.tsx`: the "deleted" rendering becomes unreachable and may be removed; nothing else in the panel changes.
- M2 `se_u4_avatar_path_ownership`: replace the INSERT policy with `bucket_id = 'avatars' and ((storage.foldername(name))[1] = (select auth.uid())::text or public.is_admin())` and the UPDATE policy with `USING bucket_id = 'avatars' and ((owner = (select auth.uid()) and (storage.foldername(name))[1] = (select auth.uid())::text) or public.is_admin())` and the same folder-or-admin rule in `WITH CHECK`; keep the policy role `public` or narrow it to `authenticated` only if review shows no caller depends on the former.
- `lib/supabase.ts`: `uploadUserAvatar` gains an optional folder; `updateProfile` passes the signed-in user's id; admin callers keep the flat name.
- Test helpers: `avatarObjectNames` lists the student's folder (or a new exact-name read by the service role) and `removeAvatarObject` verifies absence by exact name; a new `__tests__/rls/storage.test.ts` (with a test-plan header) uses actor clients' `storage.from("avatars")` and an owned-object helper for exact-name cleanup.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| R1. M2 changes policies on a Storage-owned table. | Resolved read-only: `supautils.policy_grants` grants `postgres` policy management on `storage.objects` (section 2). Main re-reads the setting at preflight; a change stops the rollout. |
| R2. Between the production deploy and the M1 apply, new code calls a function that does not exist yet, so soft delete fails on production; old code's direct delete would fail after M1 anyway. | Accepted by D5: apply M1 and M2 in one push as soon as the deploy is live, and keep the window short. Postflight checks the function before Owner QA. |
| R3. Old code uploads learner avatars to flat paths and soft-deletes directly; both fail once M1 and M2 apply. A tab opened before the deploy keeps running the old bundle. | D5 applies both only after the new deploy is live, and accepts that stale tabs fail until reloaded (no data loss). Owner QA runs in freshly loaded tabs. |
| R4. The INSERT enrollment check reads `lessons`/`enrollments` as the caller. | `lessons.course_id` is granted and enrollments expose own rows; prove with the enrolled and admin allowed paths, and `EXPLAIN` in postflight. |
| R5. A deleted comment becomes invisible to admins too, so a wrongly deleted comment can only be restored by trusted database maintenance. | Accepted by D3; no restore feature is in scope. Recorded in the migration comment. |
| R6. `db push` applies each migration in its own transaction; M2 can fail after M1 committed. | Stop on any error, record which versions committed with `list_migrations`, and ask the Owner; never retry blindly. |

- Rollout runbook: (1) green CI and Codex implementation PASS; (2) Main preflight, read-only: hosted policies, triggers and `supautils.policy_grants` match section 2; (3) merge grant, then Main confirms the production deploy of the merge is live; (4) prepare grant: `db push --linked --dry-run` lists exactly M1 and M2; (5) apply grant: apply both in one push; (6) catalog postflight by Main: exact policy expressions on `comments` and `avatars`, the function's definition, owner, `search_path` and execute privileges, `EXPLAIN` of the INSERT policy; (7) behavior postflight under the separate D8 grant: simulated-role SQL inside a rolled-back transaction, as anon and as the accounts the Owner names (a non-enrolled user, an enrolled user, an admin), on rows the Owner approves (a deleted comment hidden, INSERT refused and allowed, the function's owner success); ungranted checks stay `pending`; (8) Owner QA in fresh tabs; then SE-P4 and SE-P5 close, only when (6)–(8) passed.
- Stop when: hosted metadata differs from section 2, the dry run lists anything other than M1 and M2, any postflight check fails, or a behavior probe lacks its grant (then it stays pending); one blocker holds the whole PR.
- Rollback: M2 `.down.sql` restores the two original `avatars` policies (new `<uid>/` objects stay readable); M1 `.down.sql` restores the original SELECT, INSERT and UPDATE policies and drops the function, so code calling it must be reverted first or soft delete fails. No data changes in either direction.
