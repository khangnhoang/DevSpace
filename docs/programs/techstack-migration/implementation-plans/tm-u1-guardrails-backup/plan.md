# TM-U1 detail plan — Guardrails and backup drill

Revision: r3, 2026-11-08. Owner approval: 2026-11-08 (r3, after the Codex plan gate PASS, including the hook settings). Master plan: [plan.md](../../plan.md) (Units row TM-U1, Outcome 5, TM-F6).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: a Claude session can no longer run a command that reaches the hosted project without the Owner confirming it in the app, and the hosted database (roles, schema, data with the `auth` schema) and its Storage objects can be backed up by a written, repeatable procedure whose result has been restored once into a scratch local database and checked, so every later hosted write step of this program starts from a verified backup.

| ID | Observable result |
| --- | --- |
| AC1 | In a Claude session on this checkout, a Bash or PowerShell call whose command text runs the Supabase CLI with `--linked`, `--db-url`, `--project-ref`, `link`, `unlink`, `db push`, `db pull` or `migration repair` (with or without `--local`), or any other `supabase` invocation the classifier cannot prove local (G2), is stopped by the `PreToolUse` hook with the app's confirmation prompt (`permissionDecision: "ask"`, a reason naming the matched rule), also in auto mode; nothing runs unless the Owner confirms. |
| AC2 | The same hook asks before `supabase db reset` unless its `--workdir`, resolved against the call's working directory and normalized, equals this checkout's `.supabase-test` folder (an unresolvable path asks); and before every `psql`, `pg_dump` or `pg_restore` call except `--help` and `--version`, because libpq can take the real target from inherited variables (`PGHOSTADDR`, `PGSERVICE`) the command text does not show. |
| AC3 | The hook asks before every Supabase MCP tool that writes or changes the hosted project (`apply_migration`, `execute_sql`, `deploy_edge_function`, `create_branch`, `delete_branch`, `merge_branch`, `rebase_branch`, `reset_branch`, `create_project`, `pause_project`, `restore_project`); read-only MCP tools (`list_tables`, `list_migrations`, `list_extensions`, `get_advisors`, `get_logs`, `search_docs` and the other `get_*`/`list_*` tools) are not stopped. |
| AC4 | Local commands keep running with no extra prompt: `npx supabase start|stop|status`, `migration list --local`, `migration up --local`, `migration new <name>`, `db dump --local`, any other call with `--local` and none of the always-ask forms, `--help` and `--version`, `npm test`, `npm run test:e2e`, `npm run backup:check` (these run `psql` or the CLI inside their own processes, which the hook does not see). |
| AC5 | A hook that crashes, exceeds its timeout or prints invalid output blocks the call (fails closed), proven in a live session (CP4) through a fault switch that can only make the hook fail, never allow; malformed input is proven by a unit test. |
| AC6 | The Owner, following the runbook in their own terminal, writes a backup folder outside the repository containing `roles.sql`, `schema.sql`, `data.sql` (`--use-copy`, data of every schema the CLI dumps, `auth` included) and one folder per Storage bucket with every object, plus a manifest with the time, the CLI version and the hosted service versions; no step writes inside the repository or under `AppData`. |
| AC7 | `npm run backup:check -- <backup folder>`, run by Main under the Owner's grant for that backup, restores roles, schema and data into the scratch stack (G7) and reports pass only when all of these hold: (a) every table in `data.sql` has a restored row count equal to the rows the dump holds; (b) every table Owner decision 12 covers has a restored count equal to the hosted count Main read for that backup; (c) the restored migration history equals the hosted `list_migrations` versions; (d) every `storage.objects` row has a file of the same size (and the same MD5 where the stored ETag is a plain MD5) and no file lacks a row. Any difference is a failed check; there is no explained-difference pass. |
| AC8 | `backup:check` prints and saves only aggregates (table names, counts, totals, pass/fail, the number of mismatched objects, and on a failed step its name, exit code and SQLSTATE). Child-process output is captured in memory, reduced to those fields and discarded, never echoed or saved raw; `psql` runs with `VERBOSITY sqlstate`; before the import the scratch server's error and statement logging is off (`log_min_messages` and `log_min_error_statement` at `panic`, `log_statement = none`), so no data value is written to a server log. Mismatched object names go only to a file inside the backup folder. No row content, email, hash or object name reaches stdout, a log, a repository file or a chat. |
| AC9 | After `backup:check` ends, pass or fail, no container or volume of `devspace-backup-check` remains (`docker ps -a`, `docker volume ls`); a run killed before teardown leaves a run record, the next `backup:check` (or `backup:check -- --teardown`) removes the leftover resources before anything else and reports it, and until removal is confirmed the result is `unresolved`, never pass. |
| AC10 | `backup:check` refuses, before any write, a backup folder inside the repository or under `AppData`, a folder missing a required file, a second run while one holds the run record, a container of another project on the scratch ports, and a target that fails the Docker identity check; each refusal names the cause. |
| AC11 | After the merge, the first drill passed: State records the backup's date, the hosted versions, the result of every AC7 check and the reruns needed, with no data. |
| AC12 | Instructions match the new tools: the runbook is a `supabase-migration` reference linked from that skill's Hosted apply section, `AGENTS.md` (Commands and section 4) names `backup:check` and Main's grant-bound restore, `.claude/rules.md` names the hook and says its prompt is not a grant, and TM-F6 closes as `Done` in `future-features.md`. |

### 1.2 Scope and non-goals

- In scope (implementor): the guard module and hook script with its fault switch, the `hooks` entry in `.claude/settings.json`, the `backup:check` script and its `package.json` entry, `.gitignore` for the scratch workdir and the fault switch, unit tests for both, the CP2 rehearsal fixture, the runbook reference and the instruction edits of AC12.
- In scope (Owner): approving the hook settings; the hosted dump and Storage download in their own terminal; each per-backup grant.
- In scope (Main): hosted metadata reads (bucket list, table list), the hosted row counts and `list_migrations` for each backup, running `backup:check`, the live hook proof, State.
- Non-goals: a scheduled or automated backup, off-site copy or encryption tooling (the Owner keeps the folder, Owner decision 9 below); restoring Storage objects into a stack; signing in as a restored user (TM-U9 rehearses that); guarding commands that `npm` scripts or other programs run internally (the hook sees only the command text); any change to the test stack tooling, CI jobs or app code; upgrading the Supabase CLI (DM-F2).

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. The classifier is a pure function of the tool name, its input and the call's working directory, in its own module, unit-tested; the hook script only reads stdin and the fault switch, calls it and prints the decision. | An untestable hook silently lets a hosted command through. |
| G2. The Supabase rule runs in this order, first match wins: (1) any invocation carrying `--linked`, `--db-url`, `--project-ref`, `link`, `unlink`, `db push`, `db pull` or `migration repair` asks; (2) `db reset` passes only under AC2's `--workdir` rule (its `--local` does not count); (3) an invocation passes when it carries `--local`, or is `start`, `stop`, `status`, `init`, `migration new`, `--help`/`-h` or `--version`/`-v`; (4) everything else asks. A false positive (an extra prompt) is acceptable; a false negative on any form in AC1 to AC3 is a defect. | A new or defaulting subcommand (`migration list` without `--local`, `storage ls`, `db dump`) or `db push --local` reaches hosted unprompted. |
| G3. The classifier scans every command in a compound line (`&&`, `||`, `;`, `|`, newlines, `npx`, `npx.cmd`, `fnm exec --`, a path to the binary) case-insensitively. | `cd x && npx.cmd supabase db push` passes. |
| G4. The hook entry fails closed (`onFailure: "block"`) and matches `Bash`, `PowerShell` and the Supabase MCP tools; existing `permissions` in `.claude/settings.json` stay unchanged. | A crash allows the call; an edit drops the Playwright `ask` rules. |
| G5. The hook's prompt grants nothing: Main or an implementor asks for a confirmation only for an action already granted under `AGENTS.md` section 4, and an implementor never asks for a hosted command at all. A hook test uses only a call that, if the hook failed to stop it, either cannot reach hosted or performs a read Main may already run without asking (`AGENTS.md` section 4, read-only catalog and metadata queries). | The prompt or a test becomes a way to run a hosted action without the written grant. |
| G6. `backup:check` reads backup files only to count and compare, keeps child output as AC8 says, never copies a backup file into the repository, and refuses paths inside the repository or `AppData` (`.claude/rules.md` section 8 virtualizes `AppData` writes). | Personal data or hashes reach a log, a commit or the chat. |
| G7. The scratch stack has its own project id `devspace-backup-check`, ports 56320–56329 and generated workdir under the ignored `/.supabase-backup-check/`; its workdir has no seed and no app migrations, so the `public` schema is empty before the import; every CLI call passes `--workdir`, and a Docker identity check of `devspace-backup-check` runs before restore and teardown. Before the import starts, only the database container runs (services the schema setup needs are stopped after their setup) and its published port binds to `127.0.0.1` only; the check fails otherwise. It never touches `devspace-local` or `devspace-test`. | The restore overwrites the dev or test database, or restored accounts and rows are served by Auth, REST or Storage or reachable from the network. |
| G8. The scratch workdir pins the hosted service versions the CLI reads from `supabase/.temp` by copying only `postgres-version`, `gotrue-version` and `storage-version`, never `project-ref`, `linked-project.json` or `pooler-url` (a link would point CLI calls in that workdir at hosted); otherwise the check fails naming the mismatch. | `data.sql` fails on `auth` columns of another GoTrue version, or passes against a schema production does not have. |
| G9. A run record in the scratch workdir is written before the first Docker action and removed only after teardown is confirmed; teardown runs in `finally` and at the start of the next run when a record or a `devspace-backup-check` resource remains; a teardown failure fails the run with the container or volume name. | A killed run leaves a copy of production data in a Docker volume, or two runs share one stack. |
| G10. The runbook's hosted commands are run only by the Owner, from the repository root, with the output path outside the repository; the database password is typed at the CLI prompt only. No repo script runs a hosted command. | A script becomes a hosted path the hook cannot see; a password lands in a command or file. |

## 3. Bounded implementation hypotheses

- `scripts/agent-guard/db-command.mjs` exports `classify({ tool_name, tool_input, cwd }) → { decision: "allow" | "ask", reason }`; `.claude/hooks/db-command-guard.mjs` reads stdin and prints the `hookSpecificOutput` with `permissionDecision: "ask"` or nothing — may change if G1 and AC1 to AC5 hold.
- `.claude/settings.json` gains one `PreToolUse` entry with matcher `Bash|PowerShell|mcp__.*__(apply_migration|execute_sql|deploy_edge_function|create_branch|delete_branch|merge_branch|rebase_branch|reset_branch|create_project|pause_project|restore_project)` and command `node .claude/hooks/db-command-guard.mjs`, `onFailure: "block"`, a short timeout — the matcher may change if AC3 and G4 hold.
- `scripts/backup/check.mjs` (with pure parts in `scripts/backup/core.mjs`: row counting from `COPY … FROM stdin` blocks, path refusal, Storage comparison, error reduction to step, exit code and SQLSTATE) reuses the identity check, workdir generation and run-record helpers of `scripts/test-stack/` through small parameters (no migrations, no seed, the three version files), or copies the minimum it needs, without changing the test stack's behavior — may change if G7, G8, G9 and the unchanged test tooling hold.
- The hook's fault switch is a gitignored file next to the hook script (for example `.claude/hooks/.fault`) holding `crash`, `sleep` or `invalid`; absent or empty means normal. Main sets it with the Write tool, which the hook does not match. It can only make the hook fail — may change if AC5 holds and no switch value allows a call.
- The scratch stack starts with the database plus the Auth and Storage services so their schema migrations run at the pinned versions, then those services are stopped before the import (`start -x` for every other service) — may change if G7 and G8 hold.
- If the data-only dump omits `supabase_migrations.schema_migrations`, the runbook adds a fourth file, `--data-only --schema supabase_migrations`, so AC7 (c) can compare the history — may change if AC7 holds.
- The restore runs `psql` inside the scratch database container (`docker exec`) with `ON_ERROR_STOP=1`: `roles.sql`, `schema.sql`, then `data.sql` with `session_replication_role = replica`; hosted counts and versions are given as a JSON file Main writes into the backup folder — may change if AC7 and AC8 hold.
- The runbook is `.claude/skills/supabase-migration/references/backup-and-restore.md`, linked from Hosted apply with the read condition "before a hosted write step whose plan requires a backup" — may change if AC12 holds under `skill-authoring`.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| The local CLI cannot start the scratch stack on the hosted service versions (images missing for v2.197.0 or v1.80.2) | CP2 rehearses with the pinned versions first; if they cannot run, stop and return to Main, who brings the choice (another pin, or restoring `auth` data into the version the CLI ships with a column report) to the Owner. |
| The data-only dump or the restore errors on a Supabase-managed object (roles that exist, extension schemas, `storage` internals) | `ON_ERROR_STOP` makes it visible; the runbook records each known, explained exclusion; an unexplained error fails the drill. |
| Writes between the dump and Main's counts make AC7 (b) fail | Main counts right after the Owner's dump; a mismatch fails the drill and the backup is retaken and recounted; the Owner may pick a quiet time. |
| The hook adds latency or prompts to routine local work | AC4 rows in the unit tests; a false positive found in use becomes a classifier fix, never a broader allow. |
| Main's read-only hosted metadata queries through MCP `execute_sql`, allowed without asking by `AGENTS.md` section 4, now raise a prompt, because SQL text cannot be proven read-only | Accepted friction (Owner decision 11); the prompt adds a confirmation, not a new permission rule; read-only `list_*`/`get_*` tools stay unprompted. |
| The hook's `node` does not resolve in the shell the app starts hooks in (fnm sets Node per shell), and fail-closed then blocks every Bash and PowerShell call | The script needs no DevSpace dependency and runs on any Node the machine resolves; CP1 pipe-tests the exact configured command from Git Bash and PowerShell, and CP4 proves it in a new desktop session; if it cannot resolve, stop before CP4 and return to Main. |
| The hook does not load until a new session starts | CP4 runs in a new session; the PR body says sessions must restart. |
| A hosted command hidden in an `npm` script or another program | Named non-goal; G10 keeps hosted commands out of repo scripts; `AGENTS.md` section 4 stays the owner of the rule. |
| The Owner's machine shuts down during a check, leaving restored data in a Docker volume | G9 and AC9: the record survives; the next `backup:check` or `backup:check -- --teardown` removes it first; the runbook tells the Owner to run the teardown if no check follows. |

- Rollout runbook (Owner or hosted steps, in order): (1) the Owner approves the hook settings at plan approval; (2) after the implementation Codex PASS, CP4 in a new session; (3) commit, push, PR and merge under their own grants; (4) CP5: Main reads the hosted bucket list (metadata); the Owner runs the runbook in their own terminal (`db dump --linked` for roles, schema and data, `storage cp -r --linked` per bucket, the manifest) and gives the per-backup grant; Main reads the hosted counts and `list_migrations` right after the dump, writes them into the backup folder, then runs `npm run backup:check`. Nothing writes to hosted.
- Stop when: a check needs a hosted write; the scratch stack cannot be told apart from the dev or test stack; a restore error has no explanation; a backup file would land inside the repository or `AppData`; the hook would need `deny` or a broader allow to work.
- Rollback: revert the PR (hook entry, scripts, docs); run `backup:check -- --teardown` or remove the scratch resources and confirm no `devspace-backup-check` container or volume remains. The backup folder is the Owner's and stays.
