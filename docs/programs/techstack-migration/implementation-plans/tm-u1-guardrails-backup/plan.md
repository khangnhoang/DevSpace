# TM-U1 detail plan — Guardrails and backup drill

Revision: r4, 2026-11-08. Owner approval: r3 on 2026-11-08 after the Codex plan gate PASS; r4 (hook withdrawn, Owner decision 13) on 2026-11-08 after its Codex plan gate PASS. Master plan: [plan.md](../../plan.md) (Units row TM-U1, Outcome 5, TM-F6).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: the hosted database (roles, schema, data with the `auth` schema) and its Storage objects can be backed up by a written, repeatable procedure whose result has been restored once into a scratch local database and checked, so every later hosted write step of this program starts from a verified backup. The guardrails of this unit are the backup check's own isolation and data rules (G6 to G10) and the existing permissions of `AGENTS.md` section 4; the command hook of r1 to r3 is withdrawn (Owner decision 13).

| ID | Observable result |
| --- | --- |
| AC1 to AC5 | Withdrawn in r4 (Owner decision 13): the `PreToolUse` hook and its live proof. No hook entry, hook script, guard module, fault switch or hook test remains in the repository. |
| AC6 | The Owner, following the runbook in their own terminal, writes a backup folder outside the repository containing `roles.sql`, `schema.sql`, `data.sql` (`--use-copy`, data of every schema the CLI dumps, `auth` included) and one folder per Storage bucket with every object, plus a manifest with the time, the CLI version and the hosted service versions; no step writes inside the repository or under `AppData`. |
| AC7 | `npm run backup:check -- <backup folder>`, run by Main under the Owner's grant for that backup, restores roles, schema and data into the scratch stack (G7) and reports pass only when all of these hold: (a) every table in `data.sql` has a restored row count equal to the rows the dump holds; (b) every table Owner decision 12 covers has a restored count equal to the hosted count Main read for that backup; (c) the restored migration history equals the hosted `list_migrations` versions; (d) every `storage.objects` row has a file of the same size (and the same MD5 where the stored ETag is a plain MD5) and no file lacks a row. Any difference is a failed check; there is no explained-difference pass. |
| AC8 | `backup:check` prints and saves only aggregates (table names, counts, totals, pass/fail, the number of mismatched objects, and on a failed step its name, exit code and SQLSTATE). Child-process output is captured in memory, reduced to those fields and discarded, never echoed or saved raw; `psql` runs with `VERBOSITY sqlstate`; before the import the scratch server's error and statement logging is off (`log_min_messages` and `log_min_error_statement` at `panic`, `log_statement = none`), so no data value is written to a server log. Every error the check itself raises while reading the backup (a file or object it cannot read, a JSON or SQL file it cannot parse) is reported the same way, as a step name and an error code, never with a path below the backup folder, an object name or file content. Mismatched object names go only to a file inside the backup folder. No row content, email, hash or object name reaches stdout, a log, a repository file or a chat. |
| AC9 | After `backup:check` ends, pass or fail, no container or volume of `devspace-backup-check` remains (`docker ps -a`, `docker volume ls`); a run killed before teardown leaves a run record, the next `backup:check` (or `backup:check -- --teardown`) removes the leftover resources before anything else and reports it, and until removal is confirmed the result is `unresolved` (exit code distinct from fail), never pass, for every teardown path, `--teardown` included. Once a run has accepted the backup folder and holds exclusive ownership, and before the start-of-run cleanup or any other step that can fail, it replaces the backup folder's saved result with a non-pass result, so a failed or unresolved run never leaves an earlier pass as the latest result. A process refused before it holds ownership leaves the saved result untouched. |
| AC10 | `backup:check` refuses, before any write, a backup folder inside the repository or under `AppData`, a folder missing a required file, a second run or a `--teardown` while another live process holds the run, a container of another project on the scratch ports, and a target that fails the Docker identity check; each refusal names the cause. Taking the run is atomic: two processes started together cannot both proceed. |
| AC11 | After the merge, the first drill passed: State records the backup's date, the hosted versions, the result of every AC7 check and the reruns needed, with no data. |
| AC12 | Instructions match the tools: the runbook is a `supabase-migration` reference linked from that skill's Hosted apply section; `AGENTS.md` (Commands and section 4) names `backup:check` and Main's grant-bound restore; `.claude/rules.md`, `AGENTS.md` and `.claude/settings.json` hold no hook text or entry; TM-F6 closes as `Dropped` in `future-features.md` with Owner decision 13 as its reason. |

### 1.2 Scope and non-goals

- In scope (implementor): the `backup:check` script and its `package.json` entry, `.gitignore` for the scratch workdir, unit tests, the CP2 rehearsal fixture, the runbook reference and the instruction edits of AC12; removing every hook artifact that CP1 to CP3 added (AC1 to AC5 row).
- In scope (Owner): the hosted dump and Storage download in their own terminal; each per-backup grant.
- In scope (Main): hosted metadata reads (bucket list, table list), the hosted row counts and `list_migrations` for each backup, running `backup:check`, State.
- Non-goals: a scheduled or automated backup, off-site copy or encryption tooling (the Owner keeps the folder, Owner decision 9 below); restoring Storage objects into a stack; signing in as a restored user (TM-U9 rehearses that); any mechanism that blocks or prompts for hosted commands (a hook, a wrapper, a credential move), including for the credential exposure section 5 records (Owner decision 13); any change to the test stack tooling, CI jobs or app code; upgrading the Supabase CLI (DM-F2).

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1 to G5 | Withdrawn in r4 with the hook (Owner decision 13). |
| G6. `backup:check` reads backup files only to count and compare, keeps child output and its own errors as AC8 says, never copies a backup file into the repository, and refuses paths inside the repository or `AppData` (`.claude/rules.md` section 8 virtualizes `AppData` writes). | Personal data or hashes reach a log, a commit or the chat. |
| G7. The scratch stack has its own project id `devspace-backup-check`, ports 56320–56329 and generated workdir under the ignored `/.supabase-backup-check/`; its workdir has no seed and no app migrations, so the `public` schema is empty before the import; every CLI call passes `--workdir`, and a Docker identity check of `devspace-backup-check` runs before restore and teardown. Before the import starts, only the database container runs (services the schema setup needs are stopped after their setup) and its published port binds to `127.0.0.1` only; the check fails otherwise. It never touches `devspace-local` or `devspace-test`. | The restore overwrites the dev or test database, or restored accounts and rows are served by Auth, REST or Storage or reachable from the network. |
| G8. The scratch workdir pins the hosted service versions the CLI reads from `supabase/.temp` by copying only `postgres-version`, `gotrue-version` and `storage-version`, never `project-ref`, `linked-project.json` or `pooler-url` (a link would point CLI calls in that workdir at hosted); otherwise the check fails naming the mismatch. | `data.sql` fails on `auth` columns of another GoTrue version, or passes against a schema production does not have. |
| G9. The run is taken atomically (an exclusive create of the run record, or a lock shared by a run and `--teardown`) before the first Docker action, and released only by its owner after teardown is confirmed; teardown runs in `finally` and at the start of the next run when a stale record (its process gone) or a `devspace-backup-check` resource remains; a live owner's run is never torn down by another process; a teardown failure ends the run `unresolved` with the container or volume name. | A killed run leaves a copy of production data in a Docker volume, two runs share one stack, or `--teardown` destroys a running restore. |
| G10. The runbook's hosted commands are run only by the Owner, from the repository root, with the output path outside the repository; the database password is typed at the CLI prompt only. No repo script runs a hosted command. | A script becomes a hosted path an agent runs without the grant; a password lands in a command or file. |

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| The local CLI cannot start the scratch stack on the hosted service versions (images missing for v2.197.0 or v1.80.2) | CP2 rehearses with the pinned versions first; if they cannot run, stop and return to Main, who brings the choice (another pin, or restoring `auth` data into the version the CLI ships with a column report) to the Owner. |
| The data-only dump or the restore errors on a Supabase-managed object (roles that exist, extension schemas, `storage` internals) | `ON_ERROR_STOP` makes it visible; the runbook records each known, explained exclusion; an unexplained error fails the drill. |
| Writes between the dump and Main's counts make AC7 (b) fail | Main counts right after the Owner's dump; a mismatch fails the drill and the backup is retaken and recounted; the Owner may pick a quiet time. |
| Residual (accepted, Owner decision 13): every agent session runs as the Owner's Windows user, so it has potential access to the stores section 2 lists: a `supabase … --linked` call or a linked default could use the CLI entry if it still authenticates, and a process could read `.env.local`. Actual access depends on runtime restrictions (the sandbox, the app's permission mode and auto-mode classifier) and on authentication, neither verified here. With the repository hook removed, no repository mechanism asks before such a call; the control is procedural (`AGENTS.md` section 4 and the implementor brief) | The backup taken before every hosted write step of this program (Outcome 5) is recovery evidence for the data it covers, at the time it was taken; it does not undo a disclosure, an external effect or a write after the backup, and this unit does not rehearse restoring Storage objects into a service. Main reviews every diff and transcript claim against the repo; implementors never run hosted commands. Revisit only on an Owner request. |
| Residual (accepted): the Supabase MCP connector with its write tools may reach other Claude sessions (not verified), the GitHub CLI token has scopes that allow a push or merge, and a usable Vercel token may exist (not verified) | The same procedural control (`AGENTS.md` section 4: implementors never call the MCP, push or merge; deployment needs an explicit Owner instruction). A mistaken push or deploy is visible in GitHub and Vercel and can normally be undone by a revert or rollback, and a database write falls under the backup row above, with the same limits. |
| The Owner's machine shuts down during a check, leaving restored data in a Docker volume | G9 and AC9: the record survives; the next `backup:check` or `backup:check -- --teardown` removes it first; the runbook tells the Owner to run the teardown if no check follows. |

- Rollout runbook (Owner or hosted steps, in order): (1) after the implementation Codex PASS, CP4; (2) commit, push, PR and merge under their own grants; (3) CP5: Main reads the hosted bucket list (metadata); the Owner runs the runbook in their own terminal (`db dump --linked` for roles, schema and data, `storage cp -r --linked` per bucket, the manifest) and gives the per-backup grant; Main reads the hosted counts and `list_migrations` right after the dump, writes them into the backup folder, then runs `npm run backup:check`. Nothing writes to hosted.
- Stop when: a check needs a hosted write; the scratch stack cannot be told apart from the dev or test stack; a restore error has no explanation; a backup file would land inside the repository or `AppData`.
- Rollback: revert the PR (scripts, docs); run `backup:check -- --teardown` or remove the scratch resources and confirm no `devspace-backup-check` container or volume remains. The backup folder is the Owner's and stays.
