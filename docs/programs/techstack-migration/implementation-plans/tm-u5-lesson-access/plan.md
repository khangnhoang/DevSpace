# TM-U5 detail plan — Session gate and lesson access

Revision: r4, 2026-11-28 (corrected after the Codex plan rounds 1 to 3). Owner approval: approved 2026-11-28, after the Codex plan gate passed in round 4. Master plan: [plan.md](../../plan.md) (decisions 11, 16, 17 and 19).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: the `/learn` pages read the course-access verdict, the lesson they show (its public fields and its private `content` and `video_url`) and the course outline from the NestJS API through `lib/api.server.ts`, instead of from Supabase in the Next server. Learners and admins see the same pages, redirects and not-found screens as before. The API decides access itself, and private lesson columns leave the API only after that decision. The unit ships as one PR (decision 19), and M2 runs on its real routes on production right after the merge.

| ID | Observable result |
| --- | --- |
| AC1 | A signed-in learner enrolled in a course opens one of its lessons and sees the same title, content, previous and next lesson links and sidebar outline as before; on the seed course 2, the lesson order and the exercise link (lesson 3 has exercises, lesson 4 none) are asserted. `has_video` and `video_url` are asserted at the API (AC4), since the seed has no video. |
| AC2 | A visitor without a session who opens a lesson is sent to `/login`; a signed-in learner not enrolled in the course is sent to `/course/<slug>`; an unknown course or a lesson slug that is not in that course shows the not-found lesson screen. The same holds for the quiz page's gate. |
| AC3 | An admin who is not enrolled opens a lesson of a course, including one that the learning-order check would send an enrolled learner away from, and sees it; `LearnClient` still gets `isAdmin` true. |
| AC4 | Straight to the API, in today's order (session, then course, then access, then lesson where the route takes one): a request without a session is 401; a course slug that does not exist is 404; a session that is not enrolled and not admin is 403; on the lesson and quiz routes an enrolled or admin session asking for a lesson slug outside the course is 404; no refusal body holds `content`, `video_url` or the outline. The outline keeps today's order (chapter `order_index`, then lesson `order_index` with nulls last, then lesson `created_at`), shown on fixture chapters and lessons whose order values disagree with their insertion order. The enrolled and admin cases are 200 with each route's own fields (the lesson route with `content`, `video_url` and `has_video`; the quiz route without private columns). A lesson that has an exercise and whose `chapter_id` names a chapter of the authorized course but whose `course_id` names another course never yields its private columns or a true has-exercise marker. |
| AC5 | These server reads go through `apiFetch` and make no Supabase or service-role read: `requireCourseAccess`, the layout's outline, the lesson page's lesson and private columns and outline, and the quiz page's lesson and outline; `app/(main)/learn/[course]/[slug]/page.tsx` no longer imports `lib/supabase.admin.ts`. The quiz page's `exercises` read (until TM-U15) and the finish page's browser `profiles` read (until TM-U14) stay. |
| AC6 | A render of a lesson page and of a quiz page by GET records at least one GET to a `/api/learn` route in the API's request record and no non-GET call. |
| AC10 | When the API fails without a refusal (a 5xx, an unreachable API, a 200 whose body does not match its schema), the lesson and quiz pages show "Không thể tải bài học", render no private content and do not redirect; when only the layout's outline read fails, the page still renders and the sidebar is absent. |
| AC11 | New behavior (unit decision 1): `/learn/<course>/finish` is gated like a lesson: a visitor without a session is sent to `/login`, a signed-in learner not enrolled to `/course/<slug>`, an unknown course shows the not-found lesson screen, and an enrolled learner or an admin sees the completion screen with the sidebar as before; the student's name still comes from the browser `profiles` read. |
| AC7 | `devspace_api` gains exactly the column grants these reads need and nothing more; `__tests__/rls/api-role.test.ts` shows the new effective privileges, and the refusals it already asserts for other columns and tables still hold. |
| AC8 | M2 on production, right after the merge, on `GET /api/learn/lesson` of an existing course and lesson through the production origin, with each of two hosted fixture users' access token sent as `Authorization: Bearer` and no cookie (so `proxy.ts` cannot clear it before the API sees it): while live, each token gets 403 (the control that it passed the session guard); the same unexpired token gets 401 more than 30 seconds after its session is signed out (fixture 1) and after its user is deleted (fixture 2). A 403 within the 30-second cache window is the accepted D6 staleness; a 403 after it fails M2 and is investigated. The time of a token's first call and of a repeat call within the cache window is recorded, and their difference as "observed end-to-end first-minus-repeat latency", not as an Auth figure; M2's API-side `/auth/v1/user` round trip stays recorded as pending, because no API-side timing surface exists since TM-U3's was removed. Results go to `progress.md`; a failure goes to the Owner before TM-U13 starts. |
| AC9 | `frontend-workflow` holds the procedure for a page that reads through the API (TM-P18), written from the pages this unit moves. |

### 1.2 Scope and non-goals

- In scope: one API module for the learn reads (the access verdict, the lesson with its private columns, the outline), its additive column-grant migration and rollback, the regenerated Drizzle schema; `requireCourseAccess` and the learn layout, lesson and quiz pages calling it through `apiFetch`; the finish page's new server gate (AC11), with its client part moved beside it; `api`, `rls` and `e2e` rows for the guarantees above; the TM-P18 procedure; TM-P1 for these server reads; the TM-U16 AC7 record already in `progress.md`.
- Non-goals: everything `LearnClient` reads in the browser (completed lessons, last accessed lesson and the slug lookup of the allowed lesson, which belong to TM-U13 with progress); notes, comments and the finish page's profile read (TM-U14, TM-U6); the exercises read and grading (TM-U15); closing a Data API door, because every table this unit reads still has unmoved readers (2.); any change of look, copy or redirect target other than AC10's message and AC11; P3, P4 and T5 (TM-U13, decision 19); the browser calling `/api` for any learn data.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. The API reads the user id only from the session and the role only from `profiles` with its own query; the course and lesson come from the path or query and are looked up, never trusted as ids from the caller. | A learner reads another course's lessons by sending its id. |
| G2. `content` and `video_url` are selected only after the access decision passed, in the same handler, and no refusal path returns or logs them. | Private lesson content leaks to a non-enrolled caller or into logs. |
| G3. `requireCourseAccess` keeps its name and its shape (`{ user, course, isAdmin }`, `{ redirect }` or `{ notFound }`) with one narrowing: `user` becomes `{ id: string }`, the id the API answer names (its only reader is the quiz page's `user.id`). It gains `{ unavailable: true }` for AC10. It calls no `getCurrentUser()`: the API is the only authority, and its 401 alone maps to `/login`. The pages keep turning the shape into `redirect()`, the not-found screen or the unavailable message. | The callers and the `server-actions` contract break, a redirect target changes, or an API outage reads as "not signed in". |
| G4. When a page's own read fails without a refusal, the page renders no lesson content and does not redirect as if the learner were not enrolled (AC10); a failed outline read only removes the sidebar. Next parses every 200 body with a schema before use, and logs only the status or the error's type, never the cookie or the body. | A broken API sends every learner to the course page as if not enrolled, or renders an empty lesson as success. |
| G5. The migration only adds column grants on the named columns to `devspace_api`; it revokes the same columns first so a rollback is exact, and it touches no other role, table or policy (`supabase-migration`, trap 3). | The API role gains a table-wide privilege, or anon and authenticated lose access that unmoved code needs. |
| G6. Every route stays default-deny: none of the new routes carries `@Public()`; none carries `@Sensitive()` (not payment or admin class). | A session route becomes public, or every lesson load pays an uncached Auth call. |
| G7. No API change removes or changes a route the live frontend calls; the new routes are additions. | The previous frontend breaks while the production gate waits (decision 17). |
| G8. Every protected read is bound to the authorized course on the lesson's own `course_id`, the exercise count included, not only through `chapter_id` (the `exercises` policy authorizes on the lesson's `course_id`). | `devspace_api` bypasses RLS, so a lesson filed under another course's chapter leaks its private columns or exercise marker. |

## 2. Repository facts

Baseline: `a13c525`, checked 2026-11-28.

- `requireCourseAccess` (`lib/auth.server.ts:46-75`) reads `courses` by slug, then `profiles.role` and the caller's `enrollments` row, all with the caller's Supabase session; the lesson page and the quiz page call it (`app/(main)/learn/[course]/[slug]/page.tsx:39`, `quiz/page.tsx:19`) — justifies AC2, AC3, G3.
- The lesson page reads the lesson's public fields with the caller's session, then `content` and `video_url` with the service role after the gate (`page.tsx:44-61`) — justifies AC5, G2.
- The outline is `getLessonsByCourse` (`lib/supabase.ts:53-95`): `courses` by slug, then `chapters` with nested `lessons (id, title, slug, has_video, exercises (count))`, ordered by chapter and lesson `order_index` then lesson `created_at`. `has_exercise` comes from the RLS-filtered `exercises` count, which is nonzero only for an enrolled learner or an admin (`__tests__/rls/content.test.ts` C4, C5, C6). The layout calls it without a gate (`layout.tsx:21-22`), and the lesson and quiz pages call it again — justifies AC1, AC4 (the outline route needs the gate to keep `has_exercise` hidden from others).
- `LearnClient` reads `user_progress` and a lesson slug in the browser (`app/components/LearnClient.tsx:57-90`) — justifies the non-goal.
- `apiFetch` (`lib/api.server.ts`) forwards the request's cookies and the app `Origin` to `API_INTERNAL_URL`, GET by default, `no-store` — justifies the hypothesis of 3.
- `devspace_api` holds today: `profiles (id, role)`; `courses (id, name, slug, description, image_url, price, instructor_id)`; `chapters (id, course_id, title, order_index)`; `lessons (id, slug, course_id, chapter_id, title, has_video, word_count)`; and the TM-U4 review and instructor columns (`supabase/migrations/20261108143215_devspace_api.sql`, `20261109145730_…`, `20261110101429_…`). It has no grant on `enrollments`, `exercises`, `lessons.order_index`, `lessons.created_at`, `lessons.content` or `lessons.video_url`, and `api-role.test.ts` asserts those refusals in API-R3 (`enrollments` at line 232, the four `lessons` columns at 701-708, `exercises` at 734) — justifies AC7, G5.
- `__tests__/api/session.test.ts` already proves a signed-out and a deleted user's session are refused on the test stack (AC6 rows of TM-U3); M2 is the hosted HS256 half — justifies AC8.
- Every table this unit reads keeps unmoved Data API readers: `enrollments` and `user_progress` (`LearnClient`, the progress queries such as `lib/supabase.ts:616`, until TM-U13), `exercises` (the quiz page's read, `quiz/page.tsx:38`, until TM-U15), `profiles` (header, finish page, until TM-U14), `lessons` and `chapters` public columns (admin pages until TM-U8, `LearnClient`), and `lessons.content`/`video_url` are already closed to anon and authenticated (C3) — justifies the non-goal "no door to close".
- `lessons.chapter_id` and `lessons.course_id` are independent foreign keys (`backend/src/db/schema.ts`, `lessons_chapter_id_fkey`, `lessons_course_id_fkey`); the outline nests lessons by `chapter_id`, and the `exercises` policy authorizes on the lesson's `course_id` (`supabase/migrations/20261021185249_h2_1b_restrict_reads.sql:32-40`) — justifies G8 and the AC4 cross-course case.
- `requireCourseAccess` returns a Supabase `User` (`lib/auth.server.ts:39-42`); the API session guard exposes only `{ id }` (`backend/src/auth/decorators.ts:18`); the lesson page reads `access.course` and `access.isAdmin`, and the quiz page only `user.id` (`quiz/page.tsx:106`) — justifies G3's narrowing.
- The finish page (`app/(main)/learn/[course]/finish/page.tsx`) is a client page under the same layout with no access gate; it reads `profiles` in the browser — justifies AC5's limits and the finish-page row of 1.4.
- `__tests__/helpers/api-session.ts` `mint()` creates a fresh confirmed user with no enrollment and no role; the e2e fault hook in `backend/e2e/main.ts:55-68` only delays `/courses/home` — justifies the fixtures and the fault hook of 3.
- TM-U4's server reads (`lib/courses.server.ts`) map an API answer to `found`, `missing` or `unavailable`, log only the status or the error's type, and the course page shows "Không thể tải thông tin khóa học" for `unavailable` (`app/(main)/course/[slug]/page.tsx:17-29`); today a failed Supabase read in `requireCourseAccess` ends as the not-found lesson screen — justifies G4 and its message.
- TM-P18 is open and names the first unit that moves a page's read behind the API (`problems.md`) — justifies AC9.

## 3. Bounded implementation hypotheses

- A `backend/src/learn/` module with a controller under `/api/learn`: `GET /api/learn/lesson?course=<slug>&lesson=<slug>` returns the access verdict, the lesson's public fields, its `content` and `video_url`, and the outline; `GET /api/learn/outline?course=<slug>` returns the outline for the layout; `GET /api/learn/quiz?course=<slug>&lesson=<slug>` serves the quiz page: the verdict, the lesson's `id`, `title` and `slug` (no private column) and the outline, so the page's `exercises` read keeps using the caller's session with that lesson id. The server functions sit in a `lib/learn.server.ts` beside `lib/courses.server.ts`, and AC10's message for `unavailable`. May merge or split routes if AC1 to AC4, AC10 and G1, G2, G4, G6 hold.
- The query parameters are parsed with a schema in `lib/schemas/` (slug strings with the same bounds the URLs allow); the service runs the course lookup, `profiles.role` and the `enrollments` row in one Drizzle connection, and computes `has_exercise` with a count on `exercises.lesson_id` instead of RLS. May change if AC1 and AC4 hold.
- The refusal codes map to `requireCourseAccess`'s shape in Next: 401 to `{ redirect: "/login" }`, 403 to `{ redirect: "/course/<slug>" }`, 404 to `{ notFound: true }`, and a 5xx, a network error or a 200 that fails its response schema to `{ unavailable: true }`, which the page renders as the message of AC10. `requireCourseAccess` gets `user.id`, `course.slug` and `isAdmin` from the API answer. The response schemas live with the server functions (they are not request schemas, so not in `lib/schemas/`). May change if G3, G4 and AC10 hold.
- The layout renders the sidebar only from a 200 outline and renders no sidebar on a refusal or a failure, since the lesson and quiz pages redirect, show not found or show the unavailable message in the same render. The finish page becomes a server `page.tsx` that calls `requireCourseAccess` and renders today's client component from `finish/_components/` (frontend-workflow, route-private files). May change if AC1, AC2, AC10 and AC11 hold.
- The quiz-route and lesson-route sessions in `__tests__/api/learn.test.ts` are minted fixtures given an enrollment row or the admin role by the service role (setup only), plus, for G8, a fixture lesson with an exercise (its presence read back in setup) whose chapter and lesson name different courses, a fixture `video_url` for `has_video`, and two fixture chapters with lessons whose order values disagree with their insertion order for the outline order, all owned and removed by the file's scope. The e2e rows use the seed `student` (enrolled in course 2), `learner` and `admin` sessions. The fault hook of `backend/e2e/main.ts` gains a cookie that makes one named `/learn` route answer 500 or a malformed 200, so the outline-only case of AC10 can fail the outline while the page's own read succeeds; an unreachable API is a unit row of the server functions with `fetch` faked.
- Migration `tm_u5_api_learn_read`: `grant select (order_index, created_at, content, video_url) on public.lessons`, `grant select (user_id, course_id) on public.enrollments`, `grant select (lesson_id) on public.exercises` to `devspace_api`, each column revoked first; rollback revokes them. The exact column list may shrink to what the final queries read.
- `__tests__/api/learn.test.ts` for AC4 and G1, G2, G6, G8; `api-role.test.ts` rows updated for AC7; `__tests__/e2e/student.spec.ts` T1 extended for AC1's values, `learner.spec.ts` L2 and `public.spec.ts` S4 kept, with new rows for the admin path (AC3), the not-found paths (AC2), AC10 and the request-record check (AC6) in `api-topology.spec.ts` or the learner specs.
- The TM-P18 procedure goes to `frontend-workflow` (a short section or a reference): where the call sits (a server-only function next to the route or in `lib/`), how 401, 403, 404 and failure reach the page, and what a test fakes. May change shape if AC9 holds.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| An extra network hop per learn page (layout and page both call the API, and the API's Auth call when the cache is cold) makes lesson loads slower. | The layout and the page reuse one call where the hypothesis allows; the Owner's production smoke check notes the load; a lesson page time is read with the M2 run and recorded, not gated (D11 gates only a browser-to-`/api` screen). |
| A wrong status mapping redirects enrolled learners or hides an outage (G4). | API rows for each code, an e2e row that an API 5xx shows the error state and no redirect, CP3. |
| M2 fails on hosted (a revoked token still passes after the cache window). | Within the window the 30-second staleness is D6's accepted cost; after it, the cause is investigated and goes to the Owner before TM-U13 (decision 19). |
| M2 needs fixture users on hosted Auth, a hosted write. | The Owner's approval, covering creation, sign-out, deletion and cleanup, is asked before the merge; on every exit the run deletes each fixture it created and reads their absence back. |

- Rollout runbook, in order: Codex on the plan; the Owner approves the plan and grants implementation; one implementor runs CP1 to CP4 with local commits; Main's review and the Codex diff round, including the migration; push and the PR under their grants, and CI green; the Owner takes a backup and Main runs `npm run backup:check` on it; the migration is applied with the prepare and apply grants (`supabase-migration`, Hosted apply) and Main's postflight confirms the exact new column grants; the Owner's approval for M2's hosted fixture users; the merge under its grant; Main watches the `production-gate` run; the Owner's smoke check of AC1 to AC3 on production; Main runs M2 with the Owner's approval for the fixture users and records it with the merge's gate run in `progress.md`.
- Stop when: the migration needs any privilege other than the named column grants; a guarantee of AC4 cannot be proven by an `api` row; the gate run fails; the smoke check fails (roll back below); M2 fails (report to the Owner, no rollback needed by itself).
- Rollback, in ADR 0008 D10's order: first a frontend-only change that puts the learn pages back on their Supabase reads, keeping `/api/learn`, the migration and its rollback file on `main` (a plain revert of the PR would remove the endpoints while the gate still serves the TM-U5 frontend, and would delete a published migration file); confirm the previous behavior is live on production; only then, if wanted, remove the endpoints in a later merge. The column grants stay harmless; revoking them on hosted is a hosted write under its own grants. Nothing in this unit changes data.
