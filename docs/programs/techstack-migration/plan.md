# Master plan — techstack-migration

Progress: [progress.md](progress.md). Problems: [problems.md](problems.md). Future features: [future-features.md](future-features.md). Each unit has a detail plan at `implementation-plans/tm-u<n>-<slug>/plan.md`, written and Codex-gated when the unit opens; follow-up work from `problems.md` or `future-features.md` may have an entry plan at `implementation-plans/<id>-<slug>/plan.md` with no Units row. Roadmap: [ADR 0001](../../adr/0001-modernization-roadmap.md), step 4.

## 1. Goal and outcome

- Goal: DevSpace runs on Next.js (frontend), NestJS (backend API), PostgreSQL accessed through Drizzle, and Better Auth, with every production account, password and record kept, reached domain by domain so that production works after every merge.
- Outcome 1: the browser and the Next.js server no longer read or write the database, Auth or Storage through Supabase; every read and write goes through a NestJS endpoint that authenticates the caller, checks permission on the server and validates input with the shared Zod schemas.
- Outcome 2: sign-up, sign-in, sign-out, email verification, password reset and password change run on Better Auth; every production user signs in with their existing email and password, and keeps their user id and data.
- Outcome 3: no Supabase Auth, Storage, realtime, Data API (PostgREST) or package is a runtime dependency; the database is plain PostgreSQL that only the backend reaches, on the host the TM-U2 ADR chose (if that is the existing Supabase project's Postgres, its Data API is disabled); schema changes go through Drizzle migrations, and the local, test and CI environments run on plain PostgreSQL with the same test guarantees as before.
- Outcome 4: every entry this program owns (`problems.md` TM-P1 to TM-P13, `future-features.md` TM-F1 to TM-F6) is resolved by the unit that owns it, or dropped by the Owner.
- Outcome 5: a backup of the production database and files exists before every hosted write step of this program, and has been restored once into a scratch database and checked.
- Size and risk: large and high-risk: it replaces auth, the data access layer, permissions, payment code paths, schema ownership, hosting, CI and the test harness (`AGENTS.md` sections 2 and 3).

## 3. Shared invariants

- Production works after every merge: each unit ships alone, and a unit never leaves a screen that depends on code a later unit writes — prevents a broken production between units.
- An operation moves whole: the unit of a move is an operation and its actor (for example "an enrolled learner reads a lesson's exercises", "an admin edits a course"). When a unit moves an operation to NestJS, every call site of that operation in `app/`, `lib/` and `components/` uses the API in the same PR, and the detail plan lists the operations on the same tables that stay on Supabase until a named later unit — prevents two write paths with different rules and an untracked leftover.
- The old door closes with the move: once a moved operation is live on the API, direct Data API or Storage access that only that operation needed is revoked or narrowed for its actor (grant, RLS or Storage policy) in a compatible later step of the same unit, keeping what unmoved operations still need, and a test proves the old endpoint now refuses it (for TM-P7, an enrolled learner can no longer select `exercises.correct_answer` through PostgREST while the admin editor keeps its access) — prevents a client bypassing the new server rule through the old path.
- Authorization lives on the server: each endpoint authenticates the session and checks role and ownership itself, never trusts a client id, price or role, and validates its body with a schema from `lib/schemas` (the `server-actions` rules apply to every endpoint) — prevents the browser deciding what it may do once RLS no longer guards a path.
- An access guarantee that an `rls` test proves today is proven again by an API-level test before the path it covers stops being the enforcement — prevents losing a security guarantee silently in the move.
- One migration owner at a time: until TM-U11, schema changes are SQL files in `supabase/migrations` with a rollback in `supabase/rollbacks` under `supabase-migration`, and the Drizzle schema is generated from the database and never used to migrate; from TM-U11, Drizzle migrations own the schema from a baseline of the live schema — prevents two tools writing conflicting histories.
- User ids never change: the Better Auth user id equals today's `auth.users.id`, so `profiles`, enrollments, payments, progress, notes and comments keep their owners — prevents orphaned or reassigned data.
- Before every hosted write step (migration apply, data copy, auth cutover, file move, database move) a fresh backup exists and the TM-U1 restore check passed on it — prevents an unrecoverable production loss.
- Backups hold personal data and password hashes: they never enter the repository, a chat, a CI artifact or a log, and they live only where the Owner chooses — prevents a credential and privacy leak.
- No secret in code, docs or commands; new keys are set by the Owner in the hosting settings (`AGENTS.md` section 4) — prevents leaked credentials.
- Behavior and look stay the same unless an entry this program owns changes them; visual redesign stays with `ui-ux` — prevents scope creep in a high-risk program.
- A change that makes an instruction false (`AGENTS.md`, a skill, `.claude/rules.md`, CI) updates it in the same PR under `skill-authoring`; a new skill or a widened permission waits for the Owner — prevents agents following rules for a stack that no longer exists.
- No investment in a part a later unit replaces (ADR 0001): the Supabase auth helpers are not modernized before TM-U9 — prevents throwaway work.

## 5. Order and rollout gates

1. Program opening (this plan, docs only): Codex gate, Owner approval, then commit and PR under their own grants. Nothing reaches hosted.
2. TM-U1: the backup runbook and `backup:check` merge; the first backup is taken and restored into a scratch local PostgreSQL with the Owner's hosted-read grant, and the check result is recorded in State without any data.
3. TM-U2: the ADR is accepted before any backend code. When the ADR keeps the Supabase Postgres, TM-U11 moves no data.
4. TM-U3: the NestJS service is deployed to its host under the Owner's deploy instruction and its health endpoint answers through the production frontend's origin before any domain moves; no screen uses it yet, so production behavior is unchanged.
5. TM-U4 to TM-U8, each in this order, every hosted step after a backup (`supabase-migration`, Hosted apply): an additive migration the new code needs is applied before that code merges; the backend endpoints are deployed and answer on production before the frontend that calls them; the frontend merges and deploys and the Owner smoke-checks the moved operations; only then the restrictive migration that closes the old door is applied, and its old-endpoint refusal is checked on production. A guard migration runs at the boundary its detail plan names and Codex reviewed.
6. TM-U10 (before or after TM-U9): Storage backup; the frontend and `remotePatterns` accept both stores; uploads are fenced (paused or written to both) while a final delta copy runs; every copied object is verified; uploads switch to the new store; stored URLs are updated by migration; old objects and a URL rollback stay until the postflight passes.
7. TM-U9 cutover, in one announced window, in four phases; the detail plan gives the SQL and the rollback of each, and all four are rehearsed on a restored backup first:
   1. Compatibility phase. Backup and restore check; a server-enforced fence refuses every account mutation (sign-up, password reset and change, email change, admin create, edit of role and delete) and requests in flight drain; apply the additive migration (Better Auth tables only: the foreign keys to `auth.users` and the `handle_new_user` trigger stay); run the user copy; verify counts; deploy the code that uses Better Auth; production QA of sign-in, sign-out, protected pages and admin with migrated accounts. Nothing the previous release needs has changed, so the rollback is a redeploy of the previous release.
   2. Ownership boundary. A migration moves the foreign keys of `profiles`, `enrollments`, `payments` and the other owners from `auth.users` to the Better Auth user table and replaces `handle_new_user` with Better Auth's user-creation hook; then QA of sign-up, password reset and change, and admin create and delete, through the fence's named QA exceptions. From here the rollback is the rehearsed down migration (foreign keys and trigger back on `auth.users`) plus a copy back to `auth.users` of every account created, changed or deleted since phase 1, then the redeploy.
   3. Reopening. The fence lifts only after phase 2 QA passed and its rollback passed the rehearsal; the phase 2 rollback stays valid until phase 4.
   4. Removal. After a soak period the detail plan sets, the step that removes the remaining `auth.users` dependencies runs; after it, the way back is the backup taken before it.
8. TM-U11: backup and restore check; when the ADR chose another host, the database move in a downtime window, and production verified on the new database; Drizzle baseline equal to the live schema (compared by catalog); removal of Supabase objects and packages. The hosted Supabase project is paused only when production runs on a database independent of it; when the ADR kept its Postgres, the project stays up with its Data API, Auth and Storage disabled. Deleting the project is the Owner's step after the program closes.
9. TM-U12: per item, a Drizzle migration with a backup before each hosted apply.
10. Program close: State says completed, open entries resolved or dropped, the dependency check, a backlog review with the Owner, and the row set to `closed`.

## 6. Program risks

| Risk | Mitigation |
| --- | --- |
| The NestJS Better Auth integration (`@thallesp/nestjs-better-auth`) is community-maintained and its docs differ across versions (Express versus Fastify, guard setup) | TM-U2 pins the versions it relies on and may place Better Auth in a Next.js route instead; TM-U9 tests the auth endpoints through the deployed topology, not only in unit tests |
| Cookies across two hosts (frontend on one origin, API on another) are dropped or need third-party cookies | TM-U2 decides one browser origin (for example a same-origin rewrite to the API) and proves it in a spike before the ADR is accepted |
| Supabase's bcrypt hashes do not verify under Better Auth, or the copy skips users (no email, deleted, banned) | The official Better Auth migration guide sets bcrypt verification; TM-U9 rehearses the copy on a restored production backup, compares counts and signs in with a migrated test account before the hosted run |
| Two systems hold the rules during the transition (RLS for unmoved domains, NestJS for moved ones) | An operation moves whole and its old door closes in the same unit; RLS keeps guarding the unmoved operations until TM-U9 removes the remaining grants; each detail plan lists the operations still on Supabase |
| Latency or cold starts between the Vercel frontend and the API host make pages slow | The ADR states a latency budget and region; TM-U3 measures it on production before TM-U4 |
| The test harness (`devspace-test` Supabase stack, `rls` project, e2e seed users) is rebuilt in TM-U11 and guarantees are lost | The invariant on `rls` guarantees; TM-U11 maps every existing `rls` and e2e row to its new test before removing it |
| The program is long for a solo graduation project and may stop midway | Every unit leaves production working on a mixed stack; the Owner may pause after any unit, and State records where |
| A hosted step corrupts data or locks users out | Backup and restore check before each hosted write; additive migrations first, removals after QA; the cutover keeps `auth.users` until QA passes |
| Hosting costs or free-tier limits (database size, sleeping instances) | The ADR states the plan, limits and monthly cost, and the Owner accepts them |

## 7. Out of scope

- Visual redesign and new features beyond the entries this program owns; the learner notification bell and reply notifications in TM-F4 stay out unless the Owner adds them.
- DeepSeek or another AI provider (Owner decision 6).
- Dependency majors unrelated to the stack change (`typescript` 7, `eslint` 10, `lucide-react` 1, `recharts`): `dependency-maintenance` DM-F2.
- Social sign-in, two-factor auth and new auth methods; Better Auth plugins beyond what the migrated features need.
- Mobile apps and a public API for third parties.
- Deleting the hosted Supabase project (the Owner does it after the program closes).
